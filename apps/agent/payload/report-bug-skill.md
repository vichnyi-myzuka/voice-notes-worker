# Репорт бага бота

Це внутрішній інструмент: баг у самому боті (`vichnyi-myzuka/voice-notes-worker`) оформлюємо як issue і передаємо виправлення новій сесії. Запускай лише на прохання власника, сам не заводь issue. Для багів в інших репозиторіях цей скіл не підходить, якщо власник не назвав репозиторій явно.

## Порядок

1. Зрозумій баг із розмови: що очікувалось, що сталося, як відтворити. Якщо без цього не обійтися, постав власнику одне коротке питання через `question`; фактів, які можна знайти самому (логи, код, `gh issue list`), не питай.
2. Перевір дублікат: `gh issue list -R vichnyi-myzuka/voice-notes-worker --state open --search "<ключові слова>"`. Якщо такий issue є, не створюй новий: додай коментар із новими деталями (`gh issue comment`) і передавай у handoff його номер.
3. Створи issue: `gh issue create -R vichnyi-myzuka/voice-notes-worker --label bug --label ready-for-agent --title "<коротко, що зламано>" --body-file <файл>`. Тіло (українською) складається з розділів: «Що сталося», «Очікувалось», «Як відтворити», «Діагностика» (версії, назви сесій, фрагменти логів і помилок, підозрювані файли `шлях:рядок`), «Критерій готовності». Не клади в issue секрети, токени, фінансові чи інші приватні дані власника: прибери або замаскуй їх.
4. Передай виправлення новій сесії:

```
handoff --repo vichnyi-myzuka/voice-notes-worker --name fix-<коротка-назва> <<'EOF'
Виправ баг: issue #<номер> у vichnyi-myzuka/voice-notes-worker (<посилання>).
<Суть бага, що вже з'ясовано, підозрювані місця в коді, як перевірити виправлення.>
Працюй за звичайним порядком: діагностика, план і погодження власника, тести, PR із `Closes #<номер>`.
Поза задачею: <що не чіпати>.
EOF
```

   Нова сесія не бачить цієї розмови, тож у тексті має бути все потрібне. Команду не обгортай у pipe й нічого не дописуй у той самий виклик.
5. Після handoff скажи власнику одним реченням: номер і посилання на issue та що виправлення передано. Сам баг у цій сесії не виправляй.
