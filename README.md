# voice-notes-worker

iPhone Shortcut записує голос і шле файл на цей Cloudflare Worker. Воркер транскрибує запис через Workers AI (`whisper-large-v3-turbo`), генерує назву й summary через OpenAI `gpt-6-luna` (fallback: Workers AI `gemma-4-26b-a4b-it`) і надсилає в Telegram аудіофайл з осмисленою назвою. Якщо задано `TODOIST_TOKEN`, воркер читає проєкти, мітки й відкриті задачі з Todoist, задачі з нотатки проходять тріаж (дублікати, проєкт, мітки, пріоритет, дати), а після публікації воркер одразу створює задачі в Todoist (у підписі назви задач стають посиланнями на них у Todoist). Нотатку можна також написати текстом (див. «Текстові нотатки») або надіслати фото (див. «Фото-нотатки»). Нотатку можна відредагувати відповіддю (голосом або текстом) на неї в каналі. Задачі колись були одноразово мігровані з Things окремим скриптом (поза репозиторієм).

```
Shortcut ──POST m4a──▶ fetch (producer) ──▶ R2 + Queue ──▶ queue (consumer)
                                        │  R2 → Whisper → gpt-6-luna (або Gemma 4): summary → Todoist (/sync) → тріаж задач
                                        │  → Telegram sendAudio (підпис, без кнопок) → /sync batch у Todoist → підпис з посиланнями на задачі
                                        └─ після 4 невдалих повторів → DLQ → повідомлення про помилку в Telegram
Telegram ──відповідь (голос/текст) на нотатку──▶ вебхук ──▶ черга ──▶ правка в Todoist + підпис на місці (з посиланнями)
```

## Структура

Моно-репозиторій на npm workspaces: `apps/*` — воркери, `packages/*` — спільний код. Застосунки залежать від пакетів, але не один від одного.

    r2/                адаптери NoteRepository і TaskLedger (нотатки та задачі нотаток у R2)
    todoist/           адаптер TaskTracker для Todoist: API (/sync), команди, валідація полів задач, тріаж, налаштування проєктів і міток

### Архітектура

Залежності йдуть згори вниз: `interface` → `application` → `domain`; `infrastructure` реалізує порти домену. Ядро (`interface`, `application`, `domain`) не знає ні про Telegram, ні про Todoist, лише про порти:

- **`Channel`** (`packages/core`, `domain/channel`): звідки приходять записи й куди публікуються нотатки. Реалізація: `packages/core` → `infrastructure/telegram` (вебхук, Bot API, сутності тексту, реакції, ліміти підпису).
- **`TaskTracker`** (`domain/tracker`): знімок проєктів і міток, тріаж, створення й оновлення задач, налаштування проєктів і міток. Реалізація: `infrastructure/todoist` (`/sync`, команди, промпти й валідація полів задач).

- **`NoteRepository`** і **`TaskLedger`** (`domain/published`, `domain/tracker`): збереження нотаток і задач нотаток. Реалізація: `infrastructure/r2`.
- **`Llm`** (`packages/core`, `domain/llm`): structured output і розпізнавання голосу. Реалізація: `packages/core` → `infrastructure/llm`.

Адаптери створюються в `src/index.ts` і передаються вниз як `{ channel, tracker, notes, ledger, llm }`. Домен не імпортує `infrastructure`. Запис у R2 (аудіо, `<key>.state.json`) лишається в `application` через `Env`. Щоб підключити інший канал чи трекер, потрібно реалізувати відповідний інтерфейс; промпти тріажу при цьому належать адаптеру, бо описують модель конкретного трекера.

Службові дані каналу (`fileId`, `deleteChatId`…) лежать у `customMetadata` запису в R2, ядро передає їх каналу як є. Ключ списку задач нотатки в R2 — `notes/<id>.tasks.json` (старі нотатки з ключем `.todoist.json` читаються за запасним шляхом, поки не застаріють).

## Налаштування

```sh
npm install
cd apps/notes   # усі команди wrangler нижче запускаються звідси
npx wrangler login

# 1. R2-бакет і lifecycle rule (страховка: прибирає все старше 7 днів)
npx wrangler r2 bucket create voice-notes
npx wrangler r2 bucket lifecycle add voice-notes expire-7d --expire-days 7

# 2. Черга та dead-letter queue
npx wrangler queues create voice-notes
npx wrangler queues create voice-notes-dlq

# 3. Секрети (кожна команда інтерактивно попросить значення)
npx wrangler secret put SECRET          # будь-який довгий випадковий рядок, напр. `openssl rand -hex 32`
npx wrangler secret put OPENAI_KEY      # для gpt-6-luna; без нього summary робить Gemma 4
npx wrangler secret put BOT_TOKEN       # від @BotFather
npx wrangler secret put CHAT_ID         # ваш chat id (напишіть боту, потім https://api.telegram.org/bot<TOKEN>/getUpdates)
# необов'язково, для голосових прямо з Telegram (див. «Голосові з Telegram»):
npx wrangler secret put TG_WEBHOOK_SECRET  # `openssl rand -hex 32`
npx wrangler secret put TG_OWNER_ID        # ваш Telegram user id (для особистого чату з ботом)
# необов'язково, але без нього нотатки йдуть без тріажу й задач у Todoist:
npx wrangler secret put TODOIST_TOKEN   # Todoist → Settings → Integrations → Developer → API token

# 4. Деплой
npx wrangler deploy
```

Після деплою wrangler покаже URL на кшталт `https://notes.example.com`.

Логи: `npx wrangler tail` або Workers Logs у дашборді.

## iPhone Shortcut

Дії по порядку:

1. **Record Audio**: Audio Quality: Normal, Start Recording: Immediately, Finish Recording: On Tap.
2. **Get Contents of URL**:
   - URL: `https://notes.example.com`
   - Method: **POST**
   - Headers: `x-secret` = значення `SECRET`
   - Request Body: **Form**, поле `audio`: тип **File** → **Recorded Audio**
3. (опційно) **Show Notification** з **Contents of URL**: воркер відповідає `ok`, обробка йде у фоні.

Проєкти, мітки й задачі шорткат не надсилає: воркер бере їх із Todoist сам. Будь-які інші поля форми ігноруються.

## Тести, lint і git-хуки

- `npm run lint` — oxlint (`src`, `test` кожного застосунку й пакета).
- `npm run typecheck` — `tsc --noEmit`.
- `npm test` — vitest: наскрізний e2e через `worker.fetch` і `worker.queue` з підміненими OpenAI, Telegram і Todoist (`apps/notes/test/e2e.test.ts`: вебхук → нотатка → задача → «Видали нотатку»), unit-тести кроків обробки (`apps/notes/test/steps.test.ts`), маршрутизація `handleFetch` із каналом-заглушкою (`apps/notes/test/inbox.test.ts`), наскрізні `processNote` і `processEdit` з підміненими OpenAI і Telegram (`apps/notes/test/process-note.test.ts`: публікація, правка й повтор після збою без повторного LLM), чистої логіки (підпис і хештеги, розбір відповідей моделі й ключі задач при редагуванні, валідація полів задач Todoist, `planOps` (create/update/delete), `buildCommands`, `applyOps` і `syncTasks` з підміненим `fetch`, перехід на літній час, фільтр вхідних повідомлень Telegram). Тести Todoist — у `apps/notes/test/todoist.test.ts` і `apps/notes/test/sync-tasks.test.ts`. Без мережі й без LLM — у `apps/notes/test/fake-env.ts` R2 у пам'яті.
- `npm run check` — усе разом (lint + typecheck + test).

Git-хуки лежать в `.githooks/` і вмикаються автоматично після `npm install` (скрипт `prepare` ставить `core.hooksPath`):
- pre-commit = lint + typecheck;
- pre-push = `npm run check`.

Якість промптів (регресії LLM) перевіряється вручну на записах з `apps/notes/test-audio/` (див. розділ нижче), а не в хуках: це платні моделі й десятки секунд.

У надзвичайній ситуації обійти хуки: `git commit --no-verify`.

## Голосові з Telegram

Окрім шорткату, запис (або текст) можна надіслати прямо в Telegram:

- **У канал `CHAT_ID`** — голосове або аудіо **без підпису**. Бот ставить ✍, а після публікації нотатки видаляє оригінал (потрібне право адміна «видаляти повідомлення»). Голосові й аудіо з підписом ігноруються: так бот не чіпає власних нотаток (фото приймаються й з підписом, див. «Фото-нотатки»). Текст у каналі — це текстова нотатка (див. нижче), якщо він не починається з «/» і не є відповіддю на нотатку.
- **В особистий чат з ботом** — лише від `TG_OWNER_ID`; бот ставить ✍, нотатка з'являється в каналі.

Тріаж працює так само, як і для шорткату: проєкти, мітки й задачі воркер бере з Todoist. Аудіо пересилається в канал за `file_id`. Ліміт Bot API на завантаження — 20 МБ. Whisper приймає Telegram OGG/Opus напряму.

Увімкнути вебхук (після цього `getUpdates` перестає працювати):

```sh
source .env && curl "https://api.telegram.org/bot$BOT_TOKEN/setWebhook" \
  -d url=https://notes.example.com/telegram \
  -d secret_token=$TG_WEBHOOK_SECRET \
  --data-urlencode 'allowed_updates=["message","channel_post"]' -d drop_pending_updates=true
```

## Текстові нотатки

Нотатку можна написати текстом:

- **У канал `CHAT_ID`** — звичайне повідомлення (не відповідь на нотатку, без підпису) або **в особистий чат з ботом** від `TG_OWNER_ID`.
- Бот ставить ✍ і обробляє текст як голосову нотатку, але **без транскрипції** (Whisper не викликається): текст і є транскриптом.
- Опублікована нотатка — **текстове повідомлення** (`sendMessage`): назва, summary, задачі, хештеги, а оригінальний текст — у **згорнутій цитаті** під ними. Дуже довгий оригінал обрізається з «…», щоб усе вмістилось у 4096 символів.
- Оригінальне повідомлення з каналу після публікації видаляється (як для голосових); в особистому чаті воно лишається.
- Тріаж, автододавання в Todoist і команди налаштування працюють так само.
- **Редагування** відповіддю працює так само, але оновлюється текст повідомлення (`editMessageText`), а цитата оригіналу зберігається.
- Повідомлення, що починаються з «/» (наприклад `/start`), ігноруються: це команди, а не нотатки.

## Фото-нотатки

Нотатку можна надіслати **фото** (з підписом або без) у канал `CHAT_ID` чи в особистий чат з ботом від `TG_OWNER_ID`:

- Модель з vision (`gpt-6-luna`, fallback — Gemma 4) читає зображення: дослівно переписує текст на ньому й коротко описує, що на фото. Підпис автора, опис і текст з фото стають «транскриптом», а далі все як у текстової нотатки: назва, summary, задачі, тріаж, автододавання в Todoist.
- Нотатка публікується як **фото з підписом** (`sendPhoto` за `file_id`, підпис до 1024 символів); оригінал з каналу видаляється.
- Фото додається **коментарем-вкладенням** («📷 Фото з нотатки») до кожної створеної з нотатки задачі в Todoist (`/api/v1/uploads` + `note_add`). Задачі, додані пізніше правкою, фото не отримують.
- Редагування — відповіддю на нотатку, як зазвичай (оновлюється підпис фото). Фото у відповідь на нотатку — це нова нотатка, а не правка.
- Альбом (кілька фото одним повідомленням) — кожне фото окремою нотаткою. Зображення, надіслане файлом (без стиснення), не обробляється.
- Підпис до фото зберігається в R2 окремим об'єктом `<key>.caption` (у `customMetadata` 1024 символи кирилиці можуть не влізти).

## Порожні й скасовані записи

Якщо в записі лише тиша, шум або типові «галюцинації» Whisper на тиші, або якщо автор голосом скасовує запис («скасуй», «відміна, не зберігай»), модель повертає `discard`. Тоді воркер нічого не публікує, не робить тріаж і видаляє файл (а для повідомлення з каналу — і оригінал). У логах: `<key> discarded: empty|cancelled`. Фрази про реальні речі («скасувати зустріч») — це задачі, а не скасування.

## Редагування нотатки

Нотатку редагують **відповіддю на неї в каналі** (на iPhone: свайп повідомлення вліво) — **голосовим** або **текстом**. Кнопки «Редагувати» немає: Telegram Bot API не вміє відкрити поле відповіді з кнопки. Інструкція («прибери другу задачу», «перенеси зустріч на п'ятницю», «перейменуй на…») розшифровується (текстова відповідь іде без Whisper одразу в модель редагування), LLM повертає оновлену нотатку, тріаж задач робиться заново, зміни одразу застосовуються в Todoist, і повідомлення оновлюється на місці (`editMessageCaption`, аудіо не змінюється; для текстової нотатки — `editMessageText`). Відповідь-правка видаляється з каналу одразу після отримання (без ✍), а на нотатці стоїть 👨‍💻, поки правка не застосується (якщо правка остаточно не вдалась і пішла в DLQ, 👨‍💻 теж знімається).

- Нотатки для редагування зберігаються в R2 (`notes/<id>.json`, `notes/msg-<message_id>`) і живуть 7 днів, як усе в бакеті.
- Модель редагування бачить задачі разом з полями Todoist (проєкт, мітки, пріоритет, `due`, дедлайн, подробиці) і стабільним ключем (`t1`, `t2`…) і міняє лише те, що просить інструкція («зроби все на сьогодні» → `due` = дата правки для всіх). Назви змінюються лише на явне прохання перейменувати; перенесення в часі міняє тільки `due`/дедлайн. Summary та ключові думки узгоджуються з правкою (напр. змінена дата). «Сьогодні»/«завтра» в правці рахуються від дати правки, а в оригінальному записі — від дати запису.
- **Оновлення в Todoist.** Без кнопки: зміни застосовуються одразу. Змінені задачі оновлюються за ID (`item_update`, плюс `item_move`, якщо змінився проєкт), нові створюються (`item_add`), прибрані видаляються (`item_delete`). Стан нотатки (ключ задачі → ID у Todoist) лежить у R2: `notes/<id>.tasks.json`.
- Після виконання назви задач, що вже в Todoist, стають посиланнями `https://app.todoist.com/app/task/<id>` (через `caption_entities`); маркери лишаються «•».
- **Видалення нотатки.** Відповідь «видали нотатку» (голосом або текстом) видаляє всю нотатку: ще відкриті задачі в Todoist (`item_delete`), повідомлення з нотаткою в каналі, саму відповідь і записи нотатки в R2. Виконані задачі лишаються в історії Todoist. Прибрати одну задачу («видали задачу про Netflix») — звичайна правка, нотатка лишається.
- ⚠️ Telegram не повідомляє ботів про видалені повідомлення, тож якщо видалити нотатку в Telegram вручну, задачі в Todoist **не** видаляться — використовуй команду «видали нотатку».
- «Скасуй» в інструкції скасовує саме правку; нотатка лишається як була.

## Дата й час задач

Дата виконання може мати час: «до 13:00», «о 19:00» → `2026-11-10 13:00` (у Todoist — «плаваючий» час у твоєму часовому поясі, з нагадуваннями). Дедлайн у Todoist — лише дата; він ставиться, тільки якщо названо окремий пізніший крайній термін, і не дублює дату виконання.

### Нагадування

Модель повертає `reminders` лише коли автор явно просить («нагадай…»); саме по собі «о 16:00» нагадування не створює.

- «нагадай за годину» → relative, `before:60` — за N хвилин до часу виконання. Працює лише якщо в `due` є час, інакше відкидається.
- «нагадай завтра о 9» → absolute, `2026-11-11T09:00` (у Todoist — «плаваючий» час). Приймаються `today HH:MM`, `tomorrow HH:MM`, `YYYY-MM-DD HH:MM`; нагадування лише з датою, без часу, відкидається.
- Некоректні значення відкидаються, повтори прибираються.
- У Todoist це команди `reminder_add` (`relative` з `minute_offset` або `absolute` з `due`). Окремо від них Todoist Pro сам нагадує про задачі з часом — за налаштуваннями користувача (автонагадування); воркер їх не чіпає.
- **Редагування відповіддю:** «нагадай за 30 хвилин» чи «прибери нагадування» змінює лише нагадування. Якщо вони змінились, старі видаляються (`reminder_delete`) і додаються нові; якщо ні — команд нагадувань немає. ID нагадувань лежать у `notes/<id>.tasks.json`. Старі нотатки без `reminders` вважаються такими, що нагадувань не мають.
- У підписі: `🔔 −60 хв` (relative) і `🔔 2026-11-11 09:00` (absolute).

## Повторювані задачі

Якщо автор каже, що задача повторюється, модель повертає `recurrence` — фразу Todoist англійською, що починається з `every` (для підпису ще й `recurrence_label` українською). Усе, що не починається з `every`, відкидається.

| Сказано | `recurrence` |
|---|---|
| «щопонеділка о 9» | `every monday at 9:00` |
| «щодня» / «у будні» | `every day` / `every weekday` |
| «кожні два тижні» | `every 2 weeks` |
| «щомісяця 5-го» | `every month on the 5th` |
| «щороку 1 березня» | `every year on march 1` |

- `due` — дата першого виконання (з часом, якщо названо); у Todoist іде фраза: `due: {string, lang: "en"}` замість дати.
- У підписі: `🔁 щопонеділка о 9:00`.
- **Редагування відповіддю:** «зроби щовівторка» змінює повтор, «прибери повтор» знімає його. Зміна повтору — звичайне оновлення задачі.
- **Якщо Todoist не розпізнав фразу** (`INVALID_DATE`): задачу створюють повторним запитом без повтору, з датою першого виконання (у лог іде `console.error`). У підписі такої задачі немає 🔁. Інші помилки, як і раніше, перериваються помилкою.

**Курси лікування й інші повтори з терміном.** «Тричі на день 7 днів», «зранку місяць» → `every day until <останній день>` (перший день курсу — день 1; для «2–3 дні» береться довший термін). Кілька разів на день Todoist в одній задачі повторювати не вміє (`every day at 9:00, 14:00` — помилка), тож задача щоденна, а частота й дозування лишаються в назві: «Полоскати горло Тантум Верде тричі на день» 🔁 щодня до 16.11.

## Хештеги

Останній рядок підпису: `#листопад_2026 #тиждень_46 #день_2026_11_09 #Work #Shopping` — місяць, ISO-тиждень, день (у `TIMEZONE`) і проєкти нових задач з тріажу. Тап на хештег у Telegram показує всі такі записи.

## Як це працює

- **Ідемпотентність.** Поруч з аудіо в R2 лежить `<key>.state.json`: транскрипт, title/summary, `audioSent`. Повторна спроба продовжує з місця, де зупинилась: не платить вдруге за Whisper/LLM і не дублює вже надіслане в Telegram. Після повного успіху обидва об'єкти видаляються, тож повторна доставка того самого повідомлення бачить, що файлу немає, і просто робить ack.
  Залишкове вікно: якщо воркер впаде рівно між успішною відповіддю Telegram і записом стану, одне повідомлення може задублюватись. Telegram не має idempotency key, тож повністю закрити це неможливо.
- **Видалення з R2:** обидва варіанти разом. Після успіху файл видаляється одразу (не лежить зайвий час, не займає місце), а lifecycle rule на 7 днів прибирає те, що не дійшло до успіху: DLQ, завеликі файли. Так файл з DLQ ще тиждень доступний для ручного розбору.
- **Файл > 25 MB**: Whisper працює ~9x швидше за реальний час (25 хв аудіо ≈ 170 с, перевірено), а consumer має 15 хв wall time, тож 25 MB (~50–100 хв аудіо) це поріг із запасом. Більші файли не ретраяться, оригінал іде в Telegram з поясненням. Якщо файл > 50 MB (ліміт upload для Bot API), надсилається лише текстове повідомлення з ключем.
- **Summary**: основна модель `gpt-6-luna` (OpenAI Responses API, `reasoning.effort: "none"`). Якщо вона недоступна (помилка API, немає кредитів, немає `OPENAI_KEY`) або повернула невалідну відповідь, пробуємо `@cf/google/gemma-4-26b-a4b-it` у Workers AI. В обох моделей вимкнений reasoning і structured output (JSON Schema), тож відповідь завжди має форму `{title, summary}`. Fallback лишається на випадок відмови моделі чи порожніх полів.
- **Якщо не впоралась жодна з двох моделей**, повідомлення ретраїться, а на останній спробі використовується fallback (title = дата/час, summary = перші 300 символів), щоб нотатка не загубилась у DLQ лише через summary.
- **Транскрипт у Telegram не надсилається**: він потрібен лише для генерації title і summary. Підпис: назва, summary (2–4 речення), потім буллетами «💡 Ключові думки» (до 5) і «✅ Задачі» (до 10). Порожні списки не показуються. Підпис до аудіо — до 1024 символів (ліміт Telegram), текстової нотатки — до 3500. Якщо не влазить, задачі мають пріоритет: спершу зникають «Ключові думки», потім скорочується summary, і лише тоді список задач закінчується рядком «…і ще N у Todoist» (у Todoist створюються всі).

## Тріаж задач для Todoist

Працює, лише якщо задано `TODOIST_TOKEN` і в нотатці є задачі.

- **Знімок**: перед тріажем (і при редагуванні) воркер читає з Todoist проєкти, мітки й відкриті задачі (`/api/v1/sync`). Нічого не зберігається, шорткат нічого не надсилає.
- **Тріаж**: один виклик `gpt-6-luna` (`reasoning.effort: "low"`, fallback Gemma 4) зі structured output. Для кожної задачі модель повертає:
  - дослівну цитату із запису (`quote`); пріоритет і дати вона виводить лише з цієї цитати, щоб терміновість однієї задачі не перекидалась на сусідні;
  - назву задачі, дублікат (`duplicate_of`), проєкт (`""` = Inbox), мітки, пріоритет p1–p4 (p4 = без пріоритету), `due` і `deadline`, а також `details` — подробиці з запису, що не влізли в назву (що саме, як, навіщо, імена, суми, адреси, переліки; нічого не вигадується).
- **Перевірки у воркері** (модель не може «вигадати»): проєкт і мітки лише з реальних (`enum` у схемі + повторна перевірка), дублікат зараховується, лише якщо така назва справді є серед відкритих задач, мітка з назвою обраного проєкту відкидається. `due` «today»/«tomorrow» перетворюється на дату від дати запису (для правок — від дати правки), інші дати лише у форматі `YYYY-MM-DD`. У підписі: `→ Work p1 @Pending 📅 2026-11-10 ⏰ 2026-11-15` або `→ Inbox`.
- **Дублікати** визначаються за змістом серед відкритих задач (лише назви). Часткові збіги («купити молоко і хліб» при наявній «Купити молоко») розпізнаються не завжди.
- **Автододавання в Todoist.** Нотатка публікується без кнопок, одразу після цього воркер виконує зміни одним batch-запитом `/sync` і редагує підпис: назви задач, що вже в Todoist, стають посиланнями на них (`https://app.todoist.com/app/task/<id>`, через `caption_entities`), маркери лишаються «•». Команди мають сталі uuid, тож повтори черги не дублюють задачі. Якщо на останній спробі Todoist усе ще недоступний, нотатка (або правка) все одно публікується з рядком «⚠️ Не вдалося оновити Todoist» у підписі. План змін (`ops`) і id запуску зберігаються в стані обробки (`<key>.state.json`), тож uuid команд не змінюються між повторами. В описі кожної задачі спершу подробиці (`details`, якщо є), під ними `🎙 <назва нотатки> (дата)` і, якщо `CHAT_ID` — канал або супергрупа (`-100…`), посилання на повідомлення в Telegram (`https://t.me/c/…/<id>`). В особистому чаті з ботом посилань на повідомлення Telegram не має. Опис задачі переписується при правці, лише якщо змінились подробиці: те, що дописано в Todoist вручну, інакше не чіпається.
- **Проєкти** (назви й **описи**) беруться з Todoist: що означає проєкт, пиши в його описі в Todoist (Edit project → Description) — модель бачить «Назва — опис», деплой не потрібен. Зараз: Work, Personal affairs, Home, Shopping, Gifts, Want.
- **Мітки, пріоритети й загальні правила** — в описі службового проєкту «⚙️ Правила» в Todoist. Проєкт може лежати в архіві (так він не заважає); щоб змінити — розархівуй, відредагуй опис, заархівуй знову; деплой не потрібен. Формат: секція `[мітки]` (рядки «Мітка — коли ставити»; у міток Todoist немає опису) і `[правила]` (довільний текст: пріоритети p1–p4, «подарунок → Gifts», «незрозуміло → Inbox» тощо). Самі мітки беруться з Todoist. Воркер не кладе в цей проєкт задачі й не враховує його як проєкт для тріажу.
- **Старі кнопки.** Обробника `callback_query` більше немає: кнопки «Додати/Оновити в Todoist» у нотатках, опублікованих до автододавання, не працюють (Todoist-задачі додавай правкою нотатки).
- Невдалий тріаж не блокує нотатку: вона прийде без задач у Todoist.

## Проєкти й мітки голосом

Голосом чи текстом (у новому записі або у відповіді-правці) можна міняти налаштування Todoist. Команда має бути явною, без слів про проєкт/мітку модель взагалі не викликається.

- «Створи проєкт Спорт — тренування і зал»
- «Додай мітку Online — коли ставити: справи, що робляться онлайн»
- «Перейменуй проєкт Home на Дім», «перейменуй мітку Errand на Дорога»
- «Видали проєкт Gifts», «видали мітку Waiting»
- «Зміни опис проєкту Work: …», «зміни опис мітки Errand: …»

Як це відображається в Todoist:

- **Опис проєкту** — це опис самого проєкту.
- **Опис мітки** — рядок «Мітка — опис» у секції `[мітки]` опису проєкту «⚙️ Правила» (у самих міток описів немає). Перейменування й видалення мітки оновлюють цей рядок. Якщо проєкту правил немає, описи міток пропускаються.
- Проєкт із відкритими задачами **архівується**, а не видаляється (його можна повернути); порожній — видаляється.
- Видалення мітки знімає її з усіх задач.
- Inbox і «⚙️ Правила» не чіпаються; мітки без пробілів; імена порівнюються без урахування регістру; конфліктні перейменування пропускаються.
- Під нотаткою з'являється блок `⚙️ Todoist:` з переліком змін (➕ ✏️ 📝 🗄 🗑). Команди налаштування не стають задачами.

Відома межа: старі нотатки й задачі зберігають старі назви проєктів і міток у підписі, доки їх не відредагувати.

## Workers AI

Whisper (і резервна Gemma 4) працюють через binding `AI`. Безкоштовна квота: 10 000 neurons на день (і на Free-плані). Whisper коштує ~47 neurons за хвилину аудіо (~200 хв на день безкоштовно), а summary однієї нотатки ~20–50 neurons. Ціни: https://developers.cloudflare.com/workers-ai/platform/pricing/

## Ліміти Cloudflare (звірено з документацією 2026-11-09)

| | Free | Paid ($5/міс) |
|---|---|---|
| Queues | доступні | доступні |
| Операції Queues | 10 000/день | 1 млн/міс + $0.40/млн |
| Retention повідомлень | 24 год (фіксовано) | 4 дні за замовчуванням, до 14 |
| Розмір повідомлення | 128 KB | 128 KB |
| Wall time consumer | 15 хв | 15 хв |
| CPU time | 10 ms | 30 с за замовчуванням, до 5 хв |
| Subrequests на виклик | 50 | 10 000 |
| Тіло вхідного запиту | 100 MB (залежить від тарифу домену) | те саме |

Один запис коштує близько 3–5 операцій Queues, тож Free вистачає з великим запасом. Код майже не використовує CPU (здебільшого чекає на мережу), тому 10 ms на Free має вистачати. Але якщо в логах з'являться `exceededCpu`, допоможе перехід на Paid.

Джерела: [Queues limits](https://developers.cloudflare.com/queues/platform/limits/), [Queues pricing](https://developers.cloudflare.com/queues/platform/pricing/), [Workers limits](https://developers.cloudflare.com/workers/platform/limits/), [Batching & retries](https://developers.cloudflare.com/queues/configuration/batching-retries/).

## CI/CD

Зміни потрапляють у `main` лише через PR, розгортання робить GitHub Actions (`.github/workflows`):

- `check.yml`: на кожен PR і перед кожним деплоєм `npm run check` (oxlint, tsc, vitest). Секретів у цьому job немає: код з PR (зокрема від агента) виконується тут, тож Cloudflare-токен йому недоступний.
- `deploy.yml`: після мержу в `main` спершу `check`, потім розгортаються лише змінені застосунки (`notes`, `sites`, `agent`; зміни в `packages/`, `package-lock.json` зачіпають усі). Вручну: Actions → deploy → Run workflow (`apps`: `all`, `notes`, `agent`, `sites`).
- `notes` і `sites` розгортаються самі (environment `production`), `agent` чекає твого схвалення (environment `production-agent`): деплой замінює контейнер, а зміна образу скидає знімки. `CLOUDFLARE_API_TOKEN` і `CLOUDFLARE_ACCOUNT_ID` лежать лише в секретах environments, не репозиторію.
- `CODEOWNERS` позначає власником `.github/`, `wrangler.toml`, `apps/agent/container/` і `apps/agent/payload/`.

Агент не має доступу до Cloudflare: його токен GitHub пушить у гілки й відкриває PR, але не має права `workflows` (змінити workflow й дістати секрет не вийде).

Домени воркерів у репозиторії не зберігаються: CI підставляє `--domain <застосунок>.$BASE_DOMAIN` (`notes.`, `agent.`, `sites.`, а для публічних сайтів `share.`). Базовий домен задає секрет `BASE_DOMAIN` в обох environments (саме секрет, а не змінна: GitHub маскує його в публічних логах як `***`). У прикладах цього README `example.com` замінюй на свій домен. Локальний аварійний деплой: `npm run deploy -w apps/<назва> -- --domain <назва>.<домен>`.

### Налаштування GitHub (робить власник)

1. **Репозиторій публічний** (Settings → General → Danger Zone): тільки так на безкоштовному плані доступні rulesets і environment-схвалення.
2. **Environments** (Settings → Environments): `production` (без обмежень) і `production-agent` (Required reviewers: ти). У кожному секрети `CLOUDFLARE_API_TOKEN` , `CLOUDFLARE_ACCOUNT_ID` і `BASE_DOMAIN` (твій базовий домен).
3. **Токен Cloudflare** (My Profile → API Tokens → Custom token) лише для одного акаунта: Account → Workers Scripts: Edit; Account → Cloudchamber (Containers): Edit; Zone → Workers Routes: Edit для `example.com`. Без DNS, Access і Billing. Якщо `wrangler deploy` скаже про нестачу права, додавай по одному.
4. **Ruleset на `main`** (Settings → Rules → Rulesets): Require a pull request (0 схвалень: схвалити власний PR неможливо), Require status checks → `check`, Block force pushes, без bypass-списку (токен агента діє від твого імені, тож bypass для admin зняв би захист).
5. **Токен агента**: fine-grained PAT на потрібні репозиторії: Contents, Pull requests: Read and write; без Workflows, Actions і Administration (`wrangler secret put GITHUB_TOKEN` в `apps/agent`).

Після цього пуш у `main` напряму заборонено всім, зокрема власнику: працюємо через PR.

## Витрати Cloudflare

`npm run cost` (або `npm run cost -- 14`) друкує витрати по днях і продуктах за останні N днів (типово 7) з Billable Usage API (alpha). У `.env` потрібні `CLOUDFLARE_API_TOKEN` (токен із правом Billing Read: My Profile → API Tokens) і `CLOUDFLARE_ACCOUNT_ID`. API віддає поточний розрахунковий період, тож днів може бути менше за запит; дані оновлюються раз на день. Показується лише плата понад безкоштовні ліміти, фіксовані підписки (Workers Paid) не входять. Те саме без токена видно в дашборді Manage Account → Billing → Billable Usage.

## Агент (`apps/agent`, прототип)

Окремий воркер із **одним спільним контейнером** Cloudflare (Durable Object `main`), у якому працює `opencode serve` (OpenCode V2: веб-інтерфейс + API `/api/...`). Сесії агентів живуть усередині нього: кожна у своїй теці `/workspace/sessions/<id>`, для репозиторію це окремий `git worktree` з гілкою `agent/<id>` від свіжої default-гілки (спільний клон у `/workspace/repos/<owner>/<name>`), без репозиторію порожня тека. Воркер створює сесію, ставить агенту задачу і повертає посилання на неї. Усі сесії видно в одному веб-інтерфейсі. Доступ — лише через Cloudflare Access.

```
POST /api/sessions {prompt, repo?: "owner/name", id?}  → {id, url}   створити сесію й одразу поставити задачу (ідемпотентно за id)
GET  /api/sessions/<id>                                → {status}: working | idle | stopped
POST /api/sessions/<id>/messages {text}                → уточнення в ту саму сесію
POST /api/sessions/<id>/abort                          → зупинити поточну роботу агента (сесія лишається)
GET  /api/computer                                      → стан контейнера: running, час активності, alarm, знімок, відкриті SSE-потоки
GET  /api/computer/connections                          → running; з `?detail=1` ще й чи слухає SSH (порт 22), скільки SSH-з'єднань і скільки з'єднань воркера з OpenCode. Сплячий контейнер не будить, але `detail` читає `/proc` через `exec`, а `exec` продовжує життя контейнера (перевірено): не опитуй у циклі
POST /api/computer/snapshot                            → примусово зберегти диск контейнера (після змін поза сесіями, наприклад SSH)
GET  /s/<id>                                           → редірект на сторінку цієї сесії: /server/<base64url origin>/session/<id OpenCode>
будь-який інший шлях                                   → проксі у веб-інтерфейс OpenCode
```

Наш `id` лишається ключем ідемпотентності, відповідність `id → id сесії OpenCode` лежить у сховищі Durable Object. Підготовку теки (`git clone`/`fetch`, `git worktree add --no-track -b agent/<id>`) робить ідемпотентний `session-prep` з образу: Durable Object запускає його через `container.exec` (exec не успадковує env контейнера, тож токен GitHub передається явно) і по черзі, щоб паралельні клони не псували один одного. Worktree видаляються лише вручну (автоприбирання потрібне в #7).

Порт `Agent` (`domain/agent`: start, followUp, status, abort, serve, link, snapshot) реалізує `infrastructure/container` (Durable Object `AgentSession` + контейнер; назва історична, перейменування потребувало б міграції); HTTP-шар знає лише порт. Статус не будить контейнер, що спить (`stopped`). Диск контейнера тимчасовий, тому стан зберігається знімками (див. «Знімки диска»).

Усі сесії ділять ресурси `standard-1` (4 ГБ, 1 vCPU), контейнер не засинає, поки хоч одна працює.

**Форматування повідомлень.** Повідомлення бота йдуть як HTML Telegram: посилання вбудовані в текст (`🔗 Відкрити сесію`, `me/app#13` замість повного URL, голі адреси скорочуються), а Markdown агента (`**жирний**`, `` `код` ``, `[текст](url)`, заголовки, списки) перетворюється на форматування; HTML від моделі екранується, а якщо Telegram відхилить розмітку, повідомлення йде простим текстом. Відповідь-уточнення знаходить сесію й за прихованою адресою (`text_link`).

**Чат без сміття: один пост на сесію.** Бот не шле окремих повідомлень про стан: пост із задачею (шапка: завдання й репозиторій) оновлюється на місці. Спершу `⏳ Працює`, далі, поки агент працює, `⏳ Працює · редагує README.md` (дія береться з подій інструментів OpenCode `session.tool.input.started`/`session.tool.called`; оновлення не частіше ніж раз на 4 с, `AGENT_PROGRESS_MS`; з команд bash показується лише назва програми, бо в аргументах можуть бути токени), по завершенні шапка (скорочена до 400 символів) і підсумок агента або `⏹ Зупинено`/помилка. Відповідь-уточнення знову ставить у пості `⏳ Працює` (пост сесії агент пам'ятає, відповідати можна на нього), а саме уточнення видаляється з чату. Команди `/status`, `/stop`, `/delete` теж видаляються після виконання (відповідь бота лишається). Поки сесія працює, на пості ще й 👨‍💻. Якщо пост видалено чи Telegram не дав відредагувати, підсумок надходить новим повідомленням. Мінус редагування: Telegram не сповіщає про зміну поста, тож про завершення звук не лунає; історія завжди в самій сесії.

**Репозиторій із вільної мови.** Окрім префікса `owner/name: задача`, для нової сесії бот сам вибирає репозиторій із фрази («давай попрацюємо над нашим ботом»). Відомі репозиторії з описами задані змінною воркера `AGENT_REPOS` у `apps/agent/wrangler.toml` (JSON `[{repo, about}]`, `about` — як ти його називаєш). Один виклик моделі Workers AI обирає зі списку або «жоден»: за замовчуванням «жоден», створення нового (сайт, скрипт) ніколи не прив'язується до репозиторію. Модель мусить навести дослівну цитату з твоєї фрази, що вказує на репозиторій; якщо цитати у фразі немає, вибір відкидається, так само як відповідь поза списком. Що вибрано, видно в пості (`📦 owner/name`); помилився — видали сесію (`/delete`) і напиши з префіксом. Новий репозиторій: додай елемент у `AGENT_REPOS` і задеплой.

**Назва теки й гілки.** Тека сесії й гілка називаються за змістом задачі, із семантичним типом: `agent/feat-session-delete-18` (тека `/workspace/sessions/feat-session-delete-18`). Той самий виклик моделі, що вибирає репозиторій, дає тип (`feat`, `fix`, `docs`, `refactor`, `test`, `chore`) і коротку назву; суфікс — номер повідомлення Telegram (унікальність). Назва проходить очищення (kebab-case, до 40 символів); якщо модель не відповіла чи відповідь непридатна, лишається технічний id (`tg-<чат>-<повідомлення>`). Технічний id сесії лишається ключем у сховищі й посиланні.

**Видалення сесії:** `/delete` відповіддю на пост у Telegram (або `DELETE /api/sessions/<id>`): зникають сесія в OpenCode, її worktree, запис стеження, пост у чаті і **сайти, які вона опублікувала** (`publish` веде список назв у `/workspace/published/<тека сесії>`, `/delete` викликає для кожної `publish --delete`; перепублікація назви з іншої сесії забирає сайт собі, тож чужий сайт не видалиться; сайти, опубліковані до цієї зміни чи не з теки сесії, лишаються й видаляються вручну: `publish --delete <назва>`); бот при цьому нічого не пише (пост і команда просто зникають; повідомлення лише якщо сесії не знайдено). Гілка `agent/<назва>` у спільному клоні видаляється лише тоді, коли роботу не втрачено: її кінчик уже збігається з `origin/<гілка>` (запушено) або з головною гілкою (нічого не закомічено). Незапушені коміти лишаються в гілці, незакомічені зміни втрачаються.

**Деплой і контейнер: сесії не губляться.** Знімок відновлюється завжди, навіть якщо образ відтоді змінився (він сам визначає файлову систему, тож старий образ піднімається з усією історією сесій). Тому деплой нічого не скидає. Усе, що змінюється часто (`AGENTS.md` агента, `publish`, `session-prep`, git-хук), лежить у `apps/agent/payload/`, а не в образі: воркер розкладає ці файли в контейнер сам при кожному старті й коли їхній вміст змінився (відбиток у сховищі DO). Нові сесії одразу працюють з актуальним, старі зберігають історію зі своїм контекстом (OpenCode підхоплює зміну глобального `AGENTS.md` перед наступним запитом). Образ (`container/Dockerfile`: Node, git, OpenCode, `claude`, `entrypoint.sh`) змінюється рідко й застосовується лише за командою `/update` у чаті: контейнер зупиняється, знімок видаляється, наступне завдання стартує з поточного образу, а сесії скидаються. Поки агент працює, бот проситиме `/update force` (перериває роботу). Те саме робить `DELETE /api/computer/snapshot`.

### Інструкції агента

Агент не знає свого середовища сам, тому воркер кладе в контейнер `apps/agent/payload/AGENTS.md`: де він (спільний контейнер, своя тека й гілка `agent/<id>`), що переживає сон, як працювати з git і GitHub (пуш лише у свою гілку, PR через REST API, `gh` немає), чого не друкувати (секрети), як завершувати (короткий підсумок українською, бо він іде в Telegram). Файл лежить у `apps/agent/payload/AGENTS.md`, а воркер розкладає його в `~/.config/opencode/AGENTS.md` (читає OpenCode) і `~/.claude/CLAUDE.md` (читає `claude` за провайдером Claude Agent). Це глобальний рівень; `AGENTS.md` самого репозиторію агент читає додатково. Змінюєш файл: достатньо `wrangler deploy`, образ і сесії не чіпаються.

### Сайти агента (`apps/sites`)

Агент може опублікувати маленький статичний проєкт (сторінку, звіт, артефакт). У контейнері команда `publish <тека> <назва>` (`rclone` + перевірки назви, `index.html`, ліміти 50 МБ / 1000 файлів / 20 МБ на файл, без прихованих файлів і `node_modules`) синхронізує теку з R2-бакетом `agent-sites`, а воркер `apps/sites` віддає її на `https://sites.example.com/<назва>/` (корінь показує список сайтів, теки віддають `index.html`, `/<назва>` без слеша перенаправляється на `/<назва>/`). Доступ лише через Cloudflare Access, воркер ще й сам перевіряє JWT (`verifyAccess` з `core`). Це лише статика: у контейнері немає ключів Cloudflare для деплою воркерів, бекенди не підтримуються. Про команду агент дізнається з глобального `AGENTS.md` (розділ «Publishing small static sites»). Усі сайти живуть на одному origin, тож сторінки одного сайту технічно можуть читати інший: це нормально для приватного сховища одного власника, але не клади туди чужий код.

Налаштування (кроки в Cloudflare лише твої):

1. Бакет `agent-sites` створено (`npx wrangler r2 bucket create agent-sites`).
2. **Токен R2 лише на цей бакет**: Cloudflare → R2 → Manage API tokens → Create API token, права **Object Read & Write**, у Specify bucket обери `agent-sites`. З результату потрібні Access Key ID, Secret Access Key і endpoint (`https://<account-id>.r2.cloudflarestorage.com`).
3. Секрети воркера агента (`cd apps/agent`): `npx wrangler secret put R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `R2_ENDPOINT`, `SITES_BASE_URL` (значення `https://sites.example.com`). Вони потрапляють у контейнер, інших секретів там не додається.
4. Access для сайтів: Zero Trust → Access → Applications → Self-hosted, hostname `sites.example.com`, політика **Allow** лише твоя пошта. Запиши AUD цього застосунку й виконай у `apps/sites`: `npx wrangler secret put ACCESS_AUD` і `ACCESS_TEAM_DOMAIN` (той самий team domain, що в агента). Без цього воркер відповідає `503`.
5. Деплой (CI робить це сам; локально з доменом): `npm run deploy -w apps/sites -- --domain sites.<домен>` (домен підключає `--domain`, див. «CI/CD») і `npm run deploy -w apps/agent` (`publish` воркер сам розкладає в контейнер).

#### Публічні сайти (`share.<домен>`)

Щоб ділитися з іншими людьми, агент публікує сайт командою `publish --public <тека> <назва>`; він відкривається без входу на `https://share.<домен>/<назва>/`. Агент робить це **лише за явною вказівкою** в завданні (так написано в його `AGENTS.md`), за замовчуванням усе приватне.

- Це той самий воркер `apps/sites`, розгорнутий у wrangler-середовищі `public` (`npm run deploy:public -w apps/sites`; CI робить це разом із `sites`, домен `share.$BASE_DOMAIN`). Змінна `PUBLIC=1` вимикає перевірку Access. Бакет окремий, `agent-sites-public`, і прив'язаний явно, тож приватні сайти не можуть потрапити на публічний хост помилкою.
- Захист публічного хоста: лише статика; `Content-Security-Policy` (без відправки форм, без запитів на чужі сервери, без фреймів), `X-Robots-Tag: noindex, nofollow`, список сайтів не показується (посилання знають лише ті, кому їх надіслали); окремий піддомен, cookie приватних сайтів сюди не потрапляють. Ліміти розміру ті самі.
- Публічні сайти **не належать сесії**: `/delete` їх не видаляє (посилання, яким уже поділились, не ламаються). Зняти публікацію: `publish --public --delete <назва>` (скажи агентові).
- Окремий ключ R2 лише на публічний бакет: змінні агента `PUBLIC_R2_ACCESS_KEY_ID`, `PUBLIC_R2_SECRET_ACCESS_KEY`, `PUBLIC_SITES_BASE_URL` (endpoint спільний, `R2_ENDPOINT`).

Налаштування (кроки в Cloudflare лише твої):

1. `npx wrangler r2 bucket create agent-sites-public`.
2. R2 → Manage API tokens → ще один токен, **Object Read & Write**, у Specify bucket лише `agent-sites-public`. Потрібні Access Key ID і Secret Access Key.
3. Секрети агента (`cd apps/agent`): `npx wrangler secret put PUBLIC_R2_ACCESS_KEY_ID`, `PUBLIC_R2_SECRET_ACCESS_KEY`, `PUBLIC_SITES_BASE_URL` (значення `https://share.<домен>`). Access для `share.` **не створюй**: хост відкритий навмисно.
4. Після мержу CI розгорне `share.` разом із `sites`; токен Cloudflare у CI має право на DNS/маршрути зони (як для решти доменів). Потім `npm run deploy -w apps/agent` (схвалення `production-agent`).

### Запобіжники агента

- **Секрети.** У контейнер передається лише `OPENCODE_PASSWORD`, `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `GITHUB_TOKEN`, `CLAUDE_CODE_OAUTH_TOKEN` і змінні публікації сайтів (`R2_*`, `SITES_BASE_URL`, `PUBLIC_*`; білий список `containerEnv`, є тест). Токени Todoist і бота нотаток живуть в іншому воркері й у воркері агента їх немає; секрети чату (`BOT_TOKEN`, `TG_WEBHOOK_SECRET`, `CHAT_ID`) і Access до контейнера не потрапляють.
- **Гілки.** У образі системний `core.hooksPath` вказує на теку, куди воркер кладе `pre-push` (з `payload/`), що відхиляє пуш у `main` і `master`; агент працює в `agent/<id>`. Це запобіжник від випадковості (`--no-verify` його обходить), справжній захист налаштовується в GitHub: для кожного репозиторію, яким користується агент, увімкни **rule/branch protection** на `main` (вимагати PR, заборонити прямі пуші й force-push), а токен `GITHUB_TOKEN` зроби fine-grained лише для потрібних репозиторіїв із правами Contents і Pull requests (read/write), без Workflows і Administration. Токен не вміє пушити в захищену гілку.
- **Сон.** Контейнер засинає через годину без запитів (`AGENT_INACTIVITY_MS`); `exec`, відкриті з'єднання й SSE продовжують його життя (див. `GET /api/computer`).
- **Ліміти.** Поки хтось працює, alarm кожні 15 с перевіряє всі активні сесії (і з чату, і з веб-інтерфейсу): вартість понад `AGENT_MAX_COST_USD` (за замовчуванням 5) чи токенів (вхід + вихід + reasoning, без кешу) понад `AGENT_MAX_TOKENS` (за замовчуванням 3 млн) перериває сесію, а для сесій із чату приходить `⛔ Сесію зупинено: …`. Перша перевірка сесії з веб-інтерфейсу може відбутись із затримкою до 5 хв (до першого alarm). За підписки Claude `cost` у OpenCode може бути нульовим чи умовним, тож надійніший ліміт за токенами; реальні значення подивись у `/status`.

### Чат з агентом у Telegram

Окремий бот (не бот нотаток) працює так само, як бот нотаток: канал `CHAT_ID` (бот адмін з правом видаляти повідомлення) і особистий чат із ботом від `TG_OWNER_ID`. Голосове чи аудіо розпізнає Whisper (Workers AI, українська), текст іде як є. Бот ставить ✍ і створює сесію (id `tg-<chat>-<message_id>`):

- **У каналі** оригінал замінюється постом: текст задачі (для голосового `🗣` і розшифровка) та посилання `https://agent.example.com/s/<id>`; оригінал видаляється. У канал дописують лише адміни, тож окремої перевірки відправника немає.
- **У приваті** бот відповідає посиланням (для голосового ще й показує, що розібрав), оригінал лишається.

**Холодний старт.** Запуск контейнера й клон репозиторію тривають хвилини, а `ctx.waitUntil` після відповіді вебхуку живе лише ~30 с (далі роботу мовчки обривають: лишалась реакція ✍ і нічого більше). Тому бот не чекає: розібравши завдання (Whisper, вибір репозиторію), він шле пост `⏳ Запускаю` і передає завдання Durable Object (`begin`; для уточнення `resume`). DO зберігає його як `job:<id>` і виконує в alarm (до 15 хв): пост стає `⏳ Запускаю контейнер`, потім `⏳ Працює`. Збій повторюється до 6 разів із паузою 15 с, після цього пост показує `⚠️ Не вдалося запустити агента`. `/delete` скасовує завдання, що ще не запустилось. Повторна доставка того самого повідомлення не створює другу сесію й другу відповідь (`begin` ідемпотентний; прийняте завдання `link` показує як `pending`). Чужі користувачі, інші канали й групи ігноруються мовчки; файл понад 20 МБ чи порожня транскрипція дають підказку без сесії. Telegram одразу отримує `200`, а Whisper і холодний старт контейнера йдуть у фоні (`waitUntil`).

Керування сесією з чату:

- **Репозиторій.** Текст, що починається з `owner/name: задача`, відкриває сесію в worktree цього репозиторію (у пості з'являється `📦 owner/name`); без префікса задача йде в порожню теку. Для голосового префікс не розпізнається: репозиторій задавай текстом.
- **Уточнення.** Відповідь (голосом чи текстом) на пост бота з посиланням стає уточненням у ту саму сесію. Сесію бот знаходить за посиланням `/s/tg-…` у тексті поста, на який ти відповів (Telegram віддає його в `reply_to_message`), окремого сховища відповідностей немає. Відповідь на інше повідомлення — нова задача.
- **`/status`** (відповіддю на пост із сесією): ⏳ працює / 💤 чекає на відповідь / ✅ завершила / ❌ завершилась помилкою / ⏹ зупинена / 💤 контейнер спить, плюс вартість і токени. **`/stop`** перериває роботу; наступне уточнення продовжує її.
- **Результат без запиту.** Після `start` і кожного уточнення Durable Object стежить за сесією. Він підписується на потік подій OpenCode (SSE `/api/event`), тож підсумок з'являється в пості одразу, щойно сесія завершилась (`session.execution.succeeded/failed/interrupted`), без очікування опитування. Потік відкритий лише поки є за чим стежити. Страховкою лишається alarm: поки сесія працює, він спрацьовує кожні 15 с (ліміти витрат, обрив потоку, подія до початку стеження), а коли робота закінчилась, у той самий чат іде підсумок: останнє повідомлення агента (до 3000 символів; там зазвичай посилання на PR) і посилання на сесію, або `❌ Помилка: …`. Якщо сесію зупинено вручну, повідомлення не приходить, а якщо контейнер зупинився посеред роботи, приходить попередження. Сесія, запущена через веб-інтерфейс, не відстежується (підсумок лише для сесій із чату).

Налаштування (один крок у Cloudflare, бо вебхук має йти повз Access):

1. У @BotFather створи **окремого** бота й візьми токен. Створи канал (приватний), додай бота адміном із правом публікувати й видаляти повідомлення, `CHAT_ID` каналу має вигляд `-100…`.
2. Секрети воркера: `cd apps/agent && npx wrangler secret put BOT_TOKEN`, так само `TG_WEBHOOK_SECRET` (довільний довгий випадковий рядок), `TG_OWNER_ID` (твій числовий id у Telegram) і `CHAT_ID`.
3. Cloudflare Zero Trust → Access → Applications → додай застосунок Self-hosted для `agent.example.com` зі шляхом `telegram` і політикою **Bypass** (Everyone). Без цього Access відповідає Telegram логіном, і вебхук не доходить. Решта хоста лишається за Access; `/telegram` захищає секретний заголовок `x-telegram-bot-api-secret-token`.
4. Вебхук: `source .env && curl "https://api.telegram.org/bot$AGENT_BOT_TOKEN/setWebhook" -d url=https://agent.example.com/telegram -d secret_token=$AGENT_TG_WEBHOOK_SECRET --data-urlencode 'allowed_updates=["message","channel_post"]'` (у `.env` значення агента під іншими іменами, ніж у бота нотаток).

### SSH у контейнер

`npm run ssh -w apps/agent` (сам знаходить інстанс `main`; зі своєю командою: `npm run ssh -w apps/agent -- ls /workspace`) або вручну `npx wrangler containers ssh <INSTANCE_ID>` (id: `npx wrangler containers instances`). Якщо ключ має пароль, додай його в агент: `ssh-add --apple-use-keychain ~/.ssh/id_ed25519` (інакше wrangler відповідає `Permission denied (publickey)`). Публічний ed25519-ключ лежить у `wrangler.toml` (`[[containers.authorized_keys]]`), порту назовні немає, вхід лише через твій акаунт Cloudflare. Контейнер має вже працювати: SSH його не будить і **не утримує від сну**. Зміни, зроблені через SSH, воркер не бачить, тож після роботи виконай `POST /api/computer/snapshot` (за Access), інакше вони зникнуть разом із диском при сні. Агент не має доступу до `wrangler` і акаунта Cloudflare.

Захист у два шари: Cloudflare Access перед воркером і перевірка його JWT (`Cf-Access-Jwt-Assertion`: підпис RS256 за ключами команди, `aud`, `iss`, `exp`) у самому воркері; без `ACCESS_TEAM_DOMAIN`/`ACCESS_AUD` воркер відповідає 503. Пароль OpenCode (basic auth) підставляє воркер, у браузері його вводити не треба.

### Налаштування (потрібні ваші дії)

```sh
# 1. Docker (Docker Desktop або Colima) має працювати: wrangler збирає образ із apps/agent/container/Dockerfile
cd apps/agent

# 2. Секрети
npx wrangler secret put OPENCODE_PASSWORD          # довгий випадковий рядок (пароль OpenCode V2, користувач завжди `opencode`)
npx wrangler secret put ANTHROPIC_API_KEY          # або OPENAI_API_KEY: ключ моделі для OpenCode
npx wrangler secret put CLAUDE_CODE_OAUTH_TOKEN    # або замість ключа: токен підписки Claude (див. «Підписка Claude»)
npx wrangler secret put GITHUB_TOKEN               # необов'язково: для приватних репозиторіїв і пушу гілок

# 3. Деплой (перші хвилини після нього контейнери ще розгортаються)
npm run deploy
```

4. У Cloudflare Zero Trust створити застосунок Access (Self-hosted) для `agent.example.com` (або в налаштуваннях воркера увімкнути Cloudflare Access), політика: ваша пошта. З застосунку взяти **Application Audience (AUD) tag**, а team domain — `<team>.cloudflareaccess.com`.
5. `npx wrangler secret put ACCESS_AUD` і `npx wrangler secret put ACCESS_TEAM_DOMAIN`.
6. Перевірка (після входу через Access у браузері): `POST /api/sessions` з тілом `{"prompt":"…"}` (наприклад, з DevTools або `curl` із токеном Access Service Token) → відкрити `url` з відповіді з телефона.

Локально: `npm run dev -w apps/agent` (потрібен Docker; `LOCAL_DEV` вимикає перевірку Access).

### Відкриті питання прототипу

Перевірено на Cloudflare: кілька сесій в одному контейнері (worktree, порожня тека), прямі посилання `/s/<id>`, веб-термінал (WebSocket через проксі, потрібне прибирання `Origin`), SSH, ручний знімок, сон і відновлення зі знімком зі збереженням змін, зроблених через SSH. Не виміряно: ціна й холодний старт `standard-1`, час відновлення на великих репо. Відкрита вкладка, термінал чи SSH тримають контейнер від сну: стан дивись у `GET /api/computer`. Варіант без контейнера (OpenCode SDK у Durable Object) прибрано: без файлової системи, shell і git він не вміє клонувати репозиторії (є в історії git).

### Знімки диска (стан сесії між снами)

Контейнер засинає після години без запитів і втрачає диск (база OpenCode з історією, `/workspace`). Щоб сесія це пережила, `AgentSession` знімає диск знімками Cloudflare (`snapshotContainer`, політика `durable_object`):

- Після активності (`start`, `followUp`, зміни з веб-інтерфейсу) планується alarm через 5 хв. Якщо жоден агент не працює і з минулого знімка були зміни, диск знімається, а handle (`id`, образ, час) лягає в сховище Durable Object. Поки агент працює, alarm повторюється. Коли змін немає, alarm не перепланується (постійний alarm не давав би контейнеру заснути).
- Після сну `start`/`followUp`/веб-інтерфейс стартують контейнер зі знімка: ті самі сесії OpenCode з історією, клони й worktree, `entrypoint.sh` виконується знову (токен GitHub віддає credential helper з env (не `insteadOf`: той вшиває токен в URL, і `git remote -v` його друкує), на диск він не потрапляє, інтеграція `claude-agent` вже в базі й не підключається вдруге).
- Знімок відновлюється з образу, з якого створений (інший образ не підставляється), тож зміна Dockerfile сама сесій не скидає: новий образ застосовується командою `/update`. Якщо відновлення не вдалося (термін зберігання 30 днів від створення чи останнього відновлення), знімок видаляється й старт іде з образу.
- Знімок не містить пам'яті й процесів, секрети передаються `env` при кожному старті. Максимум 20 ГБ, диск `standard-1` — 8 ГБ.

Перевірено на Cloudflare: сесія з файлом пережила сон контейнера й відкрилась зі знімка з історією (тоді ще контейнер на сесію). Знімок порожнього клону (~21–23 МБ) створюється за 7–10 с. Час відновлення й вартість зберігання на великих репозиторіях не виміряні.

Підводні камені, на які натрапили:
- `monitor()` у `waitUntil` тримає Durable Object в пам'яті до 15 хв, і таймаут простою не стартує, тому ми його не викликаємо.
- Service worker OpenCode кешує оболонку застосунку й віддає її на `/s/<id>` (помилка «Unrecognised route»): запит не доходить до воркера. Воркер сам віддає нейтральний `/sw.js` без кешу.
- Для перевірки таймаути можна скоротити змінними `AGENT_INACTIVITY_MS` і `AGENT_SNAPSHOT_INTERVAL_MS` (`wrangler deploy --var …`).

### Підписка Claude замість API-ключа

З OpenCode 2.2.3 є провайдер **Claude Agent**: OpenCode запускає встановлений у контейнері незмінений `claude` (Claude Code) через Agent SDK і дає йому свої інструменти (файли, shell). Образ ставить `@anthropic-ai/claude-code` (`CLAUDE_CODE_VERSION` у Dockerfile).

1. На своєму комп'ютері: `claude setup-token` (вхід у браузері, токен видається приблизно на рік).
2. `npx wrangler secret put CLAUDE_CODE_OAUTH_TOKEN` (з теки `apps/agent`). Необов'язково `CLAUDE_MODEL` (`opus`, `sonnet`, `haiku`, `fable`; за замовчуванням `sonnet`).

Із токеном воркер передає його в контейнер, після старту підключає інтеграцію `claude-agent` (інтеграції завантажуються трохи пізніше за `/api/info`, тож підключення повторюється в циклі очікування) і створює сесії з моделлю `claude-agent/<модель>`. Без токена працюють ключі `ANTHROPIC_API_KEY`/`OPENAI_API_KEY`.

Перевірено на Cloudflare (workers.dev + Access): сесія створюється, веб-інтерфейс відкривається, агент на `claude-agent/sonnet` виконав задачу (створив файл і запустив `git`) через інструменти `write`/`shell`. Воркер після старту чекає, поки моделі провайдера з'являться (інакше `Model unavailable`).

Перевірено локально в Docker: сесія на `claude-agent/sonnet` відповідає, агент створює файли й запускає команди (інструменти `write`, `shell`).

**Ризик.** Anthropic забороняє пропускати чужі запити через підписку й пропонувати вхід через claude.ai іншим; вхід власника в незмінений Claude Code на власному хості її умови не забороняють, але публічно провайдер OpenCode вона не схвалювала, і умови можуть змінитись без попередження. Довгі автономні запуски можуть швидко вичерпати ліміти підписки. Токен дає доступ до підписки: зберігай лише в `.env` і `wrangler secret`.

### Версії OpenCode

Використовується лише **OpenCode V2**. Контейнер ставить `@opencode/cli` (версія зафіксована в Dockerfile, `OPENCODE_VERSION`), запускає `opencode serve --hostname 0.0.0.0 --port 4096` (веб-інтерфейс віддає сам сервер) і приймає basic auth з паролем `OPENCODE_PASSWORD`. Клієнт воркера працює з API V2: `GET /api/info` (готовність), `POST /api/session`, `POST /api/session/{id}/prompt`, `GET /api/session/active`, `POST /api/session/{id}/interrupt`; відповіді загорнуті в `{data}`. Варіант на SDK (`@opencode/sdk/workerd`) теж V2. V1 не підтримується.

Перевірено локально в Docker (образ `apps/agent/container`, `-e OPENCODE_PASSWORD=…`): `/api/info`, створення сесії з `location.directory`, `prompt`, `session/active`, `interrupt` і історія відповідають клієнту воркера; без пароля API дає 401; веб-інтерфейс (`/`, статика `/_assets/*`, SSE `/api/event`) працює з basic auth, тож `opencode pair` для проксі не потрібен. Не перевірено: WebSocket/SSE саме через `getTcpPort().fetch` у Cloudflare, холодний старт і ціна `standard-1`.
