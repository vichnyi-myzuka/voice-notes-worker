# Автоматизації агента: окремий Durable Object Scheduler

**Статус.** Прийнято; реалізується частинами. Зроблено: DO `Scheduler` і HTTP API `/api/schedules` (запобіжники: підтвердження агентських розкладів через `pending`, ліміт 10, інтервал від години, пропуск запуску, поки попередній працює, ідемпотентний id сесії). Також зроблено: ендпоінт `/agent-api/schedules` (за Access: Service Token контейнера плюс секрет сесії), команда `schedule` і правила в `payload/AGENTS.md`, кнопки `✅ Активувати / ❌ Відхилити` для розкладів від агента. Telegram: `/automations` і картки з кнопками (пауза/увімкнути, запустити зараз, історія, видалити; `✏️ Змінити` кнопкою — лише у вебі, у Telegram зміна природною мовою). Веб `/automations` із формою, історією й переглядом найближчих запусків. Добовий бюджет запусків за розкладом (`AGENT_SCHEDULE_DAILY_USD`) і ліміт вартості одного запуску (`maxCostUsd`). Усі пункти першої версії реалізовано.

**Рішення.** Агент може сам планувати запуски (одноразові й за cron). Розклад зберігає окремий Durable Object `Scheduler` (SQLite, alarm на найближчий запуск) у `apps/agent`. Коли alarm спрацьовує, воркер запускає нову сесію агента тим самим шляхом, що й завдання з Telegram (`begin`), з prompt із запису. Агент керує розкладом командою `schedule` (`add`, `list`, `edit`, `delete`) з `payload/`, яка викликає API воркера із секретом сесії.

**Чому.**
- Контейнер засинає приблизно за годину без запитів, процеси після сну не переживають, тож cron, `sleep` чи таймер у контейнері ненадійні. Розклад має жити у воркері.
- Окремий DO відокремлює розклад від життя контейнера й від `AgentSession` (ADR 0001), яка й так має кілька alarm-механізмів. Розширювати її було б простіше, але змішало б дві відповідальності.
- Cron Trigger підходить лише для коду, який ми деплоїмо через PR, а агентові потрібні динамічні розклади. Queue і вебхуки відкладених запусків за часом не тримають.

**Інтерфейс.** Єдине API воркера (`/api/schedules`: список, створення, `PATCH`, пауза/відновлення, «запустити зараз», видалення, історія) і три клієнти над ним, правила й ліміти живуть лише в `Scheduler`:
- **Telegram** (швидкі дії): `/automations` показує список, картка має кнопки `⏸ Пауза / ▶️ Увімкнути`, `▶️ Запустити зараз`, `✏️ Змінити`, `📜 Історія`, `🗑 Видалити` (патерн `callback_data` з `infrastructure/chat/callback.ts`). Запуск за розкладом — звичайна сесія з позначкою «⏰ за розкладом: назва».
- **Веб `/automations`** (за тим самим Access, що й `/s/<id>`): таблиця, форма редагування prompt, розкладу й моделі з переглядом найближчих запусків, історія запусків із посиланнями на сесії.
- **Агент**: команда `schedule` і природна мова.

Редагувати можна двома способами: природною мовою (відповідь на картку, агент виконує `schedule edit` і показує оновлену картку) і структурованою формою чи кнопками (час, cron, prompt, модель без участі агента).

**Модель запису.** Назва, prompt, розклад (одноразово чи cron із часовим поясом), репозиторій і модель (необов'язково), статус (`pending`, `active`, `paused`, `done`), хто створив (агент чи власник), ліміт вартості за запуск і термін дії, наступний запуск, історія запусків (`ok`, `failed`, `skipped` і посилання на сесію).

**Запобіжники** (значення орієнтовні, уточнюються при реалізації):
- Нові розклади від агента потрібно підтвердити кнопкою `✅ Активувати / ❌ Відхилити` у Telegram (бачите prompt і час першого запуску). Згодом підтвердження можна вимкнути.
- Не більше 10 активних розкладів і мінімальний інтервал 1 година.
- Окремий добовий бюджет на запуски за розкладом, щоб вони не конкурували зі звичайними сесіями.
- Запуск ідемпотентний: id сесії складається з id розкладу й запланованого часу, тож повтор alarm не створює дві сесії (як у ADR 0002).
- Якщо настав час запуску, а попередній запуск цього розкладу ще працює, новий пропускається: в історію пишеться `skipped`, і власник отримує повідомлення. Паралельних запусків і черги немає.

**Обсяг першої версії.** Агент планує лише «запусти мене з таким prompt у такий час». Автоматизації без LLM, тобто код у воркері, які потребують PR і деплою, у першу версію не входять.

**Наслідки.**
- З'являється новий клас Durable Object і міграція в `wrangler.toml`; пізніше перейменувати клас можна лише новою міграцією.
- `interface/telegram` і новий веб-модуль не залежать один від одного (ADR 0004); спільне лежить в `infrastructure`.
- Реалізація робиться окремими PR: DO і API, ендпоінт із секретом сесії, команда `schedule` і правила в `payload/AGENTS.md`, інтерфейси Telegram і веб, ліміти, тести й `docs/`.
