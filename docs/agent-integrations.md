# Агент: сайти й MCP-інтеграції

Що агент уміє публікувати й до яких особистих даних має доступ. Загальний опис — у [agent.md](agent.md).

## Сайти агента (`apps/sites`)

Агент може опублікувати маленький статичний проєкт (сторінку, звіт, артефакт). У контейнері команда `publish <тека> <назва>` (`rclone` + перевірки назви, `index.html`, ліміти 50 МБ / 1000 файлів / 20 МБ на файл, без прихованих файлів і `node_modules`) синхронізує теку з R2-бакетом `agent-sites`, а воркер `apps/sites` віддає її на `https://sites.example.com/<назва>/` (корінь показує список сайтів, теки віддають `index.html`, `/<назва>` без слеша перенаправляється на `/<назва>/`). Доступ лише через Cloudflare Access, воркер ще й сам перевіряє JWT (`verifyAccess` з `core`). Це лише статика: у контейнері немає ключів Cloudflare для деплою воркерів, бекенди не підтримуються. Про команду агент дізнається з глобального `AGENTS.md` (розділ «Publishing small static sites»). Усі сайти живуть на одному origin, тож сторінки одного сайту технічно можуть читати інший: це нормально для приватного сховища одного власника, але не клади туди чужий код.

Налаштування (кроки в Cloudflare лише твої):

1. Бакет `agent-sites` створено (`npx wrangler r2 bucket create agent-sites`).
2. **Токен R2 лише на цей бакет**: Cloudflare → R2 → Manage API tokens → Create API token, права **Object Read & Write**, у Specify bucket обери `agent-sites`. З результату потрібні Access Key ID, Secret Access Key і endpoint (`https://<account-id>.r2.cloudflarestorage.com`).
3. Секрети воркера агента (`cd apps/agent`): `npx wrangler secret put R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `R2_ENDPOINT`, `SITES_BASE_URL` (значення `https://sites.example.com`). Вони потрапляють у контейнер, інших секретів там не додається.
4. Access для сайтів: Zero Trust → Access → Applications → Self-hosted, hostname `sites.example.com`, політика **Allow** лише твоя пошта. Запиши AUD цього застосунку й виконай у `apps/sites`: `npx wrangler secret put ACCESS_AUD` і `ACCESS_TEAM_DOMAIN` (той самий team domain, що в агента). Без цього воркер відповідає `503`.
5. Деплой (CI робить це сам; локально з доменом): `npm run deploy -w apps/sites -- --domain sites.<домен>` (домен підключає `--domain`, див. «CI/CD» у [README](../README.md)) і `npm run deploy -w apps/agent` (`publish` воркер сам розкладає в контейнер).

### Публічні сайти (`share.<домен>`)

Щоб ділитися з іншими людьми, агент публікує сайт командою `publish --public <тека> <назва>`; він відкривається без входу на `https://share.<домен>/<назва>/`. Агент робить це **лише за явною вказівкою** в завданні (так написано в його `AGENTS.md`), за замовчуванням усе приватне.

- Це той самий воркер `apps/sites`, розгорнутий у wrangler-середовищі `public` (`npm run deploy:public -w apps/sites`; CI робить це разом із `sites`, домен `share.$BASE_DOMAIN`). Змінна `PUBLIC=1` вимикає перевірку Access. Бакет окремий, `agent-sites-public`, і прив'язаний явно, тож приватні сайти не можуть потрапити на публічний хост помилкою.
- Захист публічного хоста: лише статика; `Content-Security-Policy` (без відправки форм, без запитів на чужі сервери, без фреймів), `X-Robots-Tag: noindex, nofollow`, список сайтів не показується (посилання знають лише ті, кому їх надіслали); окремий піддомен, cookie приватних сайтів сюди не потрапляють. Ліміти розміру ті самі.
- Публічні сайти **не належать сесії**: `/delete` їх не видаляє (посилання, яким уже поділились, не ламаються). Зняти публікацію: `publish --public --delete <назва>` (скажи агентові).
- Окремий ключ R2 лише на публічний бакет: змінні агента `PUBLIC_R2_ACCESS_KEY_ID`, `PUBLIC_R2_SECRET_ACCESS_KEY`, `PUBLIC_SITES_BASE_URL` (endpoint спільний, `R2_ENDPOINT`).

Налаштування (кроки в Cloudflare лише твої):

1. `npx wrangler r2 bucket create agent-sites-public`.
2. R2 → Manage API tokens → ще один токен, **Object Read & Write**, у Specify bucket лише `agent-sites-public`. Потрібні Access Key ID і Secret Access Key.
3. Секрети агента (`cd apps/agent`): `npx wrangler secret put PUBLIC_R2_ACCESS_KEY_ID`, `PUBLIC_R2_SECRET_ACCESS_KEY`, `PUBLIC_SITES_BASE_URL` (значення `https://share.<домен>`). Access для `share.` **не створюй**: хост відкритий навмисно.
4. Після мержу CI розгорне `share.` разом із `sites`; токен Cloudflare у CI має право на DNS/маршрути зони (як для решти доменів). Потім `npm run deploy -w apps/agent` (схвалення `production-agent`).

**Єдиний стиль сайтів-звітів.** Щоб усі звіти й дашборди (покупки, фінанси, діаграми) виглядали однаково, воркер кладе в контейнер скіл `report-site` (`payload/report-site-skill.md` → `~/.config/opencode/skills/report-site/SKILL.md` і `~/.claude/skills/report-site/SKILL.md`) та команду `new-report-site <тека>` (`payload/new-report-site.sh`). Агент підхоплює скіл сам за описом, без згадки в `AGENTS.md`. Скіл фіксує стек (Vite, React, Tailwind 4, компоненти в стилі shadcn/ui, Recharts, світла й темна тема, `uk-UA`, ₴) і правила вигляду, а команда створює робочий стартовий проєкт з KPI-картками, графіками й таблицею; агент лише підставляє дані. Для схем зв'язків (архітектура, послідовність викликів, цикл життя) є `DiagramCard` з блоками `Box` і стрілками `Arrow` на SVG: кнопка «На весь екран» відкриває схему з масштабуванням (колесо, щипок, подвійний клік), перетягуванням і закриттям за Esc. Змінити стиль усіх майбутніх звітів: поправ токени й компоненти у `new-report-site.sh` та правила в скілі. Шаблон збирається з нуля (перевірено `npm run build`).

## MCP Sure (особисті фінанси)

Агент може читати й змінювати дані фінансового застосунку [Sure](https://github.com/we-promise/sure) власника через його вбудований MCP (`POST /mcp`, Bearer-токен). Це **не для всіх сесій**: воркер пише `.opencode/opencode.json` з MCP-сервером `sure` у теку лише тієї сесії, якій Sure потрібен (з git файл виключається через `info/exclude`). Sure вмикається, коли:
- задача починається з `@sure …` чи голосом «шур, …» («shure», «шюр»), префікс можна поєднувати з моделлю («модель опус, шур, …»);
- або модель-роутер (`routeTask`, той самий виклик, що дає назву гілки) вирішила, що задача потребує особистих фінансів власника (витрати, рахунки, бюджет, транзакції), навіть без ключового слова. У пості сесії з'являється рядок «💰 Sure».
Прапорець зберігається в сесії, тож після сну контейнера конфіг відновлюється. Без налаштованого Sure нічого не підключається. MCP дає і запис (категорії, транзакції, бюджети), права обмежує лише користувач `MCP_USER_EMAIL` у Sure. Сесія зі Sure працює під окремим агентом OpenCode `sure` (`payload/sure-agent.md`, у тому ж `opencode.json`: `default_agent` + `agents.sure`): фінансовий аналітик, що спершу читає дані, не вигадує цифр, змінює дані лише за явним проханням, а фінансові дані не кладе в коміти, PR, issues і публічні сайти; зате може показати їх на **приватному** сайті (звичайний `publish`, див. `payload/AGENTS.md`). Підпис дії в пості для інструментів `sure_*` конкретний («дивиться транзакції (start date 2025-10-01)»), а модель-оповідач бачить аргументи викликів і пише, що саме шукають (без сум).

Налаштування:
1. У Sure (compose): `MCP_API_TOKEN` (`openssl rand -base64 32`) і `MCP_USER_EMAIL`, перезапусти контейнер.
2. Якщо Sure за тунелем з Access: Zero Trust → Access → Service Auth → створи Service Token; у політиках застосунку Sure додай правило **Service Auth** з цим токеном.
3. Секрети агента (`cd apps/agent`): `npx wrangler secret put SURE_MCP_URL` (`https://<host>/mcp`), `SURE_MCP_TOKEN`, а з Access ще `SURE_ACCESS_CLIENT_ID` і `SURE_ACCESS_CLIENT_SECRET`. Адреса йде у конфіг сесії, токени лише в env контейнера (конфіг містить посилання `{env:…}`).

## MCP Сільпо (покупки в магазині)

Те саме для офіційного MCP Сільпо (`https://mcp.silpo.ua/mcp`): агент бачить, що власник купував (історія замовлень і чеків, товари). Сільпо вмикається так само, як Sure, і незалежно від нього:
- префікс `@silpo …` чи голосом «сільпо, …» («сильпо», «сілпо»), у будь-якому порядку з моделлю й Sure;
- або модель-роутер (`groceries`) вирішила, що задачі потрібна історія покупок у Сільпо. У пості з'являється рядок «🛒 Сільпо».
Разом із Sure («шур, сільпо, зістав чеки з платежами») сесія працює під агентом `finance` (`payload/sure-agent.md` + `payload/silpo-agent.md`): він зіставляє чеки Сільпо з платежами в Sure (дата, сума, отримувач) і знаходить платежі без чека та чеки без платежу. Лише Сільпо — агент `silpo`. Дані Сільпо приватні так само, як фінансові: лише приватні сайти.

Сільпо логіниться через OAuth 2.1 (PKCE, динамічна реєстрація клієнта), тож секретів у wrangler немає. Один раз відкрий у браузері `https://<агент>/silpo/login` (за Access), увійди в Сільпо; воркер (`infrastructure/container/silpo.ts`) зберігає refresh-токен у сховищі Durable Object і сам оновлює access-токен. У контейнер іде лише короткий access-токен: він пишеться в `.opencode/opencode.json` сесії (права 600, з git виключений) при створенні теки сесії та при її відновленні після сну. Якщо Сільпо просили, а входу немає, бот одразу надсилає в чат посилання на `/silpo/login`; якщо refresh не вдався, агент у відповіді просить відкрити `/silpo/login` і не вигадує даних. Обмеження: токен у вже запущеній сесії не оновлюється, тож для дуже довгої сесії після спливання access-токена напиши уточнення (сесія відновить конфіг лише після сну контейнера). Назви інструментів Сільпо заздалегідь не відомі, підпис у пості для них загальний («викликає Сільпо: …»).

## MCP Google Calendar (розклад і події)

Агент бачить і міняє події в Google Calendar власника: «що в мене сьогодні», «додай зустріч з Олею завтра о 15:00», «перенеси стендап на пів години». Для цього сесія запускає готовий відкритий MCP-сервер [nspady/google-calendar-mcp](https://github.com/nspady/google-calendar-mcp) (MIT) локально, у контейнері (stdio). Офіційний віддалений MCP Google Workspace не використовується: він у закритому Developer Preview і вимагає акаунта Workspace. Працює зі звичайним `@gmail.com`. Календар вмикається так само, як Сільпо, незалежно від Sure й Сільпо:
- префікс `@calendar …` чи голосом «календар, …», у будь-якому порядку з моделлю, Sure і Сільпо;
- або модель-роутер (`calendar`) вирішила, що задачі потрібні події власника. У пості з'являється «📅 Календар», модель за замовчуванням haiku.

Агент сесії — `calendar` (`payload/calendar-agent.md`: часовий пояс Europe/Kyiv, спершу знайти подію, потім міняти, питати за неоднозначності, видаляти лише явно прохане), а разом із Sure чи Сільпо — `assistant` з усіма інструкціями. Інструменти: `calendar_list-events`, `calendar_create-event`, `calendar_update-event`, `calendar_delete-event`, `calendar_get-freebusy` та інші (без `manage-accounts`: входом керує воркер). Дані календаря приватні так само, як фінансові: лише приватні сайти.

Вхід робить воркер (OAuth 2.0 з PKCE), а не сам MCP-сервер, тож секрети лишаються на воркері. Потрібне одноразове налаштування:
1. У Google Cloud створи проєкт, увімкни Google Calendar API, на екрані згоди (Google Auth Platform) додай право `https://www.googleapis.com/auth/calendar` і себе в тестових користувачах.
2. Google Auth Platform → Clients → Create client → «Web application», redirect URI `https://<агент>/calendar/callback`.
3. Секрети (`cd apps/agent`): `npx wrangler secret put GOOGLE_CLIENT_ID` і `GOOGLE_CLIENT_SECRET`.
4. Один раз відкрий `https://<агент>/calendar/login` (за Access) і увійди в Google. Воркер (`infrastructure/container/logins.ts` + `@voice-notes/oauth`) зберігає refresh-токен у сховищі Durable Object і сам оновлює access-токен. У контейнер іде лише короткий access-токен: він пишеться в `.opencode/calendar/tokens.json` теки сесії (права 600, з git виключений) разом із заглушкою замість client id/secret, тож сервер не вміє оновлювати токен сам. Якщо Календар просили, а входу немає, бот одразу надсилає посилання на `/calendar/login`.

Образ контейнера встановлює сервер глобально (`CALENDAR_MCP_VERSION` у `container/Dockerfile`, збігається з версією в `payload.ts`); у контейнері зі старого знімка без нього сервер тягнеться через `npx`. Обмеження: токен у вже запущеній сесії не оновлюється (див. Сільпо); якщо екран згоди в режимі «Testing», Google скидає refresh-токен за 7 днів, тож переведи застосунок у «In production» (для особистого використання перевірка не потрібна, лише попередження «unverified app»). Підпис у пості для інструментів — «викликає Календар: …».

## Cloudflare (MCP, лише за явним запитом)

Офіційний віддалений MCP Cloudflare (`https://mcp.cloudflare.com/mcp`) дає агентові доступ до акаунта власника (воркери, DNS, R2, KV, D1, аналітика): інструменти `cloudflare_search` (пошук потрібного API) і `cloudflare_execute` (код проти Cloudflare API). Він керує акаунтом, тому звичайні сесії його не бачать і модель-роутер його не вмикає: лише явно, префіксом `@cloudflare …` чи голосом «клаудфлер, …» (у будь-якому порядку з моделлю, Sure, Сільпо й Календарем). У пості з'являється «☁️ Cloudflare»; модель за замовчуванням не змінюється.

Вхід — OAuth 2.1 з PKCE і динамічною реєстрацією клієнта, як у Сільпо, тож секретів у wrangler немає. Один раз відкрий `https://<агент>/cloudflare/login` (за Access) і підтверди права на сторінці Cloudflare. Воркер (`infrastructure/container/logins.ts` + `@voice-notes/oauth`) зберігає refresh-токен у сховищі Durable Object і сам оновлює access-токен; у контейнер іде лише короткий access-токен: він пишеться в `.opencode/opencode.json` сесії (права 600, з git виключений). Якщо Cloudflare просили, а входу немає, бот одразу надсилає посилання на `/cloudflare/login`.

Доступ лише для читання: запитуються тільки права `offline_access user:read account:read`, змінити їх конфігурацією не можна (запис навмисно не підтримується). Агент сесії — `cloudflare` (`payload/cloudflare-agent.md`: лише дивитись; якщо задача потребує змін, дає власнику кроки), а разом з іншими сервісами — `assistant`. Дані акаунта приватні: лише приватні сайти. Обмеження ті самі, що в Сільпо: токен у вже запущеній сесії не оновлюється. Підпис у пості для інструментів — «викликає Cloudflare: …».
