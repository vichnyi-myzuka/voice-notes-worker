# Агент (`apps/agent`, прототип)

Окремий воркер із **одним спільним контейнером** Cloudflare (Durable Object `main`), у якому працює `opencode serve` (OpenCode V2: веб-інтерфейс + API `/api/...`). Сесії агентів живуть усередині нього: кожна у своїй теці `/workspace/sessions/<id>`, для репозиторію це окремий `git worktree` з гілкою `agent/<id>` від свіжої default-гілки (спільний клон у `/workspace/repos/<owner>/<name>`), без репозиторію порожня тека. Воркер створює сесію, ставить агенту задачу і повертає посилання на неї. Усі сесії видно в одному веб-інтерфейсі. Доступ — лише через Cloudflare Access.

```
POST /api/sessions {prompt, repo?: "owner/name", id?}  → {id, url}   створити сесію й одразу поставити задачу (ідемпотентно за id)
GET  /api/sessions/<id>                                → {status}: working | idle | stopped
POST /api/sessions/<id>/messages {text}                → уточнення в ту саму сесію
POST /api/sessions/<id>/abort                          → зупинити поточну роботу агента (сесія лишається)
GET  /api/computer                                      → стан контейнера: running, час активності, alarm, знімок, відкриті SSE-потоки
GET  /api/computer/connections                          → running; з `?detail=1` ще й чи слухає SSH (порт 22), скільки SSH-з'єднань і скільки з'єднань воркера з OpenCode. Сплячий контейнер не будить, але `detail` читає `/proc` через `exec`, а `exec` продовжує життя контейнера (перевірено): не опитуй у циклі
POST /api/computer/snapshot                            → примусово зберегти диск контейнера (після змін поза сесіями, наприклад SSH)
GET  /s/<id>                                           → редірект на сторінку цієї сесії: /server/<base64url origin>/session/<id OpenCode>
будь-який інший шлях                                   → проксі у веб-інтерфейс OpenCode
```

Наш `id` лишається ключем ідемпотентності, відповідність `id → id сесії OpenCode` лежить у сховищі Durable Object. Підготовку теки (`git clone`/`fetch`, `git worktree add --no-track -b agent/<id>`, а для нового worktree з `package.json` — `npm ci` (є `package-lock.json`) або `npm install`; збій встановлення лише логується) робить ідемпотентний `session-prep` з образу: Durable Object запускає його через `container.exec` (exec не успадковує env контейнера, тож токен GitHub передається явно) і по черзі, щоб паралельні клони не псували один одного. Worktree видаляються лише вручну (автоприбирання потрібне в #7).

Порт `Agent` (`domain/agent`) складається з трьох частин: `Sessions` (start, followUp, status, abort, link…), `Computer` (serve, info, snapshot, resetComputer…) і `Deploys` (деплой у пості, refs); обробники беруть лише потрібні (наприклад, GitHub — `Sessions & Deploys`). Його реалізує `infrastructure/container` (Durable Object `AgentSession` + контейнер; назва історична, перейменування потребувало б міграції). Клас тримає лише сесії (завдання, стеження, підсумки); контейнер і знімки (`computer.ts`), пост у чаті з деплоєм (`posts.ts`), питання агента (`forms.ts`) і проксі веб-інтерфейсу (`proxy.ts`) — окремі модулі поруч, типи й ключі сховища — у `state.ts`, ліміти й env — у `config.ts`; HTTP-шар знає лише порт. Статус не будить контейнер, що спить (`stopped`). Диск контейнера тимчасовий, тому стан зберігається знімками (див. «Знімки диска»).

Усі сесії ділять ресурси `standard-1` (4 ГБ, 1 vCPU), контейнер не засинає, поки хоч одна працює.

**Форматування повідомлень.** Повідомлення бота йдуть як HTML Telegram: посилання вбудовані в текст (`🔗 Відкрити сесію`, `me/app#13` замість повного URL, голі адреси скорочуються), а Markdown агента (`**жирний**`, `` `код` ``, `[текст](url)`, заголовки, списки) перетворюється на форматування; Markdown-таблиці, яких Telegram не вміє, стають списками-картками (`chat/tables.ts`: перша колонка жирним, решта «Колонка: значення», у двоколонкових — «• ключ — значення»; у блоках коду таблиці не чіпаються); HTML від моделі екранується, а якщо Telegram відхилить розмітку, повідомлення йде простим текстом. Відповідь-уточнення знаходить сесію й за прихованою адресою (`text_link`).

**Чат без сміття: один пост на сесію.** Бот не шле окремих повідомлень про стан: пост із задачею (шапка: завдання й репозиторій) оновлюється на місці. Спершу `⏳ Працює`, далі, поки агент працює, `⏳ Працює · редагує README.md` (дія береться з подій інструментів OpenCode `session.tool.input.started`/`session.tool.called`; оновлення не частіше ніж раз на 4 с, `AGENT_PROGRESS_MS`; підпис дії формує маленька модель (`gpt-6-luna`, fallback Gemma 4; ключ `OPENAI_API_KEY` воркера): вона бачить завдання з шапки поста, 8 останніх дій агента (інструмент, файл, шаблон пошуку, команда з вирізаними токенами) і попередній підпис та відповідає людською мовою, напр. `⏳ Працює · шукає, де формується підпис`, а не `виконує grep`; якщо модель не відповіла за 4 с чи збійнула, показується технічний підпис («редагує README.md», «виконує npm»; з команд bash — лише назва програми), по завершенні шапка (скорочена до 400 символів) і підсумок агента або `⏹ Зупинено`/помилка (403-челендж Cloudflare перед API моделі показується як тимчасове блокування з порадою повторити відповіддю на пост). Крім того, інструкції агента (`apps/agent/payload/AGENTS.md`, розділ «Narrate what you do») просять перед кожним кроком писати одне коротке речення українською, що він робить і навіщо, тож у самій сесії видно перебіг роботи. Коли для гілки сесії вже є PR, посилання на нього має бути в кожній фінальній відповіді агента (розділ «How to finish»). Відповідь-уточнення знову ставить у пості `⏳ Працює` (пост сесії агент пам'ятає, відповідати можна на нього), а саме уточнення видаляється з чату. Команди `/status`, `/stop`, `/delete`, `/update`, `/quota` теж видаляються після виконання, а їхні відповіді (з позначкою 💨) видаляються самі через 25 с (`EPHEMERAL_MS`, бо `waitUntil` живе ~30 с після відповіді вебхуку); `/start` лишається. Поки сесія працює, на пості ще й 👨‍💻. Якщо пост видалено чи Telegram не дав відредагувати, підсумок надходить новим повідомленням. Мінус редагування: Telegram не сповіщає про зміну поста, тож про завершення звук не лунає; історія завжди в самій сесії.

**Репозиторій із вільної мови.** Окрім префікса `owner/name: задача`, для нової сесії бот сам вибирає репозиторій із фрази («давай попрацюємо над нашим ботом»). Відомі репозиторії з описами задані змінною воркера `AGENT_REPOS` у `apps/agent/wrangler.toml` (JSON `[{repo, about}]`, `about` — як ти його називаєш). Один виклик моделі Workers AI обирає зі списку або «жоден»: за замовчуванням «жоден», створення нового (сайт, скрипт) ніколи не прив'язується до репозиторію. Модель мусить навести дослівну цитату з твоєї фрази, що вказує на репозиторій; якщо цитати у фразі немає, вибір відкидається, так само як відповідь поза списком. Що вибрано, видно в пості (`📦 owner/name`); помилився — видали сесію (`/delete`) і напиши з префіксом. Новий репозиторій: додай елемент у `AGENT_REPOS` і задеплой (зараз там `voice-notes-worker` і `flappy-bird-2d`).

**Прев'ю статичних сайтів.** Для репозиторіїв-сайтів (ознака: `index.html` у корені чи в збірці; наприклад, `flappy-bird-2d`) інструкції агента (`payload/AGENTS.md`) велять після відкриття PR опублікувати гілку як приватне прев'ю `<репозиторій>-<назва сесії>` (звичайний `publish`, без `--public`) і дати посилання у фінальному повідомленні; цей крок входить у чекліст розділу «How to finish» (зміни → коміт і пуш → PR → прев'ю → фінальне повідомлення з посиланнями). Прев'ю належить сесії, тому зникає, коли сесію прибрано після мержу (чи `/delete`). Основний публічний сайт оновлюється лише після мержу: якщо в елементі `AGENT_REPOS` задано `site` (назва сайту; зараз так для `flappy-bird-2d`), то після успішного `🔀 Змерджити` воркер дописує сесії завдання: взяти змерджений `origin/main`, опублікувати його `publish --public <site>`, видалити прев'ю й відповісти публічним посиланням. Мерж не через кнопку (на GitHub) цього не запускає. Деплой основного сайту з CI не налаштовано.

**Назва теки й гілки.** Тека сесії й гілка називаються за змістом задачі, із семантичним типом: `agent/feat-session-delete-18` (тека `/workspace/sessions/feat-session-delete-18`). Той самий виклик моделі, що вибирає репозиторій, дає тип (`feat`, `fix`, `docs`, `refactor`, `test`, `chore`) і коротку назву; суфікс — номер повідомлення Telegram (унікальність). Назва проходить очищення (kebab-case, до 40 символів); якщо модель не відповіла чи відповідь непридатна, лишається технічний id (`tg-<чат>-<повідомлення>`). Технічний id сесії лишається ключем у сховищі й посиланні.

**Видалення сесії:** `/delete` відповіддю на пост у Telegram (або `DELETE /api/sessions/<id>`): зникають сесія в OpenCode, її worktree, запис стеження, пост у чаті (у приваті з ботом ще й початкове повідомлення, з якого почалась сесія; у каналі його прибрано одразу) і **сайти, які вона опублікувала** (`publish` веде список назв у `/workspace/published/<тека сесії>`, `/delete` викликає для кожної `publish --delete`; перепублікація назви з іншої сесії забирає сайт собі, тож чужий сайт не видалиться; сайти, опубліковані до цієї зміни чи не з теки сесії, лишаються й видаляються вручну: `publish --delete <назва>`); бот при цьому нічого не пише (пост і команда просто зникають; повідомлення лише якщо сесії не знайдено). Гілка `agent/<назва>` у спільному клоні видаляється лише тоді, коли роботу не втрачено: її кінчик уже збігається з `origin/<гілка>` (запушено) або з головною гілкою (нічого не закомічено). Незапушені коміти лишаються в гілці, незакомічені зміни втрачаються.

**Деплой і контейнер: сесії не губляться.** Знімок відновлюється завжди, навіть якщо образ відтоді змінився (він сам визначає файлову систему, тож старий образ піднімається з усією історією сесій). Тому деплой нічого не скидає. Усе, що змінюється часто (`AGENTS.md` агента, `publish`, `session-prep`, git-хук), лежить у `apps/agent/payload/`, а не в образі: воркер розкладає ці файли в контейнер сам при кожному старті й коли їхній вміст змінився (відбиток у сховищі DO). Нові сесії одразу працюють з актуальним, старі зберігають історію зі своїм контекстом (OpenCode підхоплює зміну глобального `AGENTS.md` перед наступним запитом). Образ (`container/Dockerfile`: Node, Python 3 (pip, venv), git, `gh`, OpenCode, `claude`, `entrypoint.sh`) змінюється рідко й застосовується лише за командою `/update` у чаті: контейнер зупиняється, знімок видаляється, наступне завдання стартує з поточного образу, а сесії скидаються. Поки агент працює, бот проситиме `/update force` (перериває роботу). Те саме робить `DELETE /api/computer/snapshot`.

Чат у Telegram і автоматизація GitHub — у [agent-chat.md](agent-chat.md); сайти агента й MCP-інтеграції (Sure, Сільпо, Google Calendar) — у [agent-integrations.md](agent-integrations.md).

## Автоматизації (розклад запусків)

Агент може запускати сесії за розкладом (ADR 0005, перша частина: DO і API). Розклад веде окремий Durable Object `Scheduler` (`infrastructure/scheduler`, клас у `wrangler.toml` з `storage = "sqlite"`, записи лежать у його сховищі під ключами `schedule:<id>`): alarm стоїть на найближчий запуск серед активних. Коли він спрацьовує, воркер створює пост у чаті власника («⏰ за розкладом: назва», тема в приватному чаті) і викликає `begin` тим самим шляхом, що й завдання з Telegram. Id сесії = `tg-sch-<id розкладу>-<запланований час>`, тож повтор alarm не створює дві сесії.

Розклад: одноразовий (`at`, ISO з зсувом) або cron із 5 полів у часовому поясі (`tz`, за замовчуванням `Europe/Kyiv`; кроки, діапазони, списки; день місяця й день тижня діють як «або»). Правила: не більше 10 активних (разом з тими, що чекають підтвердження), інтервал між запусками не менший за годину, `expiresAt` завершує розклад. Якщо попередній запуск цього розкладу ще працює, новий пропускається (`skipped` в історії й повідомлення власнику); збій запуску — `failed` й повідомлення. Статуси: `pending` (створив агент, чекає підтвердження: `resume`), `active`, `paused`, `done`. Історія зберігає 50 останніх запусків.

API (за Access): `GET|POST /api/schedules`, `GET|PATCH|DELETE /api/schedules/<id>`, `POST /api/schedules/<id>/pause|resume|run`, `GET /api/schedules/<id>/runs`. Створення через цей API вважається створеним власником (`active`).

**Команда `schedule` для агента** (`payload/schedule.sh` → `/usr/local/bin/schedule`; `list`, `add`, `edit`, `delete`; правила для агента — розділ «Automations» у `payload/AGENTS.md`). Контейнер не проходить Access, тому команда викликає `/agent-api/schedules` (ADR 0003): секрет сесії — HMAC від назви теки на `OPENCODE_PASSWORD`; `session-prep` кладе адресу воркера й секрет у `/root/.agent/schedule/<тека>.json` (адресу воркер запам'ятовує з посилання на сесію при `begin`; без неї команда в сесії недоступна). Агент лише пропонує: новий розклад і будь-яка його зміна переходять у `pending`, власнику приходить повідомлення з кнопками `✅ Активувати / ❌ Відхилити` (`sch:ok|no:<id>`). Видалення агентом діє одразу. **Telegram `/automations`:** по картці на кожну автоматизацію (стан, розклад, найближчий і останній запуск, prompt) з кнопками під стан: `⏸ Пауза` / `▶️ Увімкнути`, `▶️ Запустити зараз`, `📜 Історія` (10 останніх запусків із посиланнями на сесії), `🗑 Видалити`, а для `pending` — `✅ Активувати` / `❌ Відхилити`. Кнопки оновлюють картку на місці (`sch:<дія>:<id>`, `infrastructure/chat/schedule-card.ts`). Запуск за розкладом — звичайна сесія з постом «⏰ за розкладом: назва». Зміна: відповіддю агентові природною мовою (він виконує `schedule edit`, і зміна знову йде на підтвердження); кнопки `✏️ Змінити` немає: форма є у вебі.

**Веб `/automations`** (за тим самим Access, `interface/http/automations-page.ts`, одна статична сторінка над `/api/schedules`): таблиця карток зі станом і діями (активувати/пауза/увімкнути, запустити зараз, видалити), історія запусків із посиланнями на сесії `/s/<id>`, форма створення й зміни (назва, prompt, один раз чи cron з поясом, репозиторій, модель, термін дії) з переглядом п'яти найближчих запусків (`POST /api/schedules/preview`: ті самі перевірки, що й при створенні). Час для одноразового запуску вводиться за часом браузера. Порожні репозиторій, модель і термін дії знімають значення.

**Потрібна дія власника:** у Cloudflare Zero Trust додати Bypass для шляху `/agent-api/*` (як для `/telegram` і `/github`), інакше Access не пропустить контейнер.

## Інструкції агента

Агент не знає свого середовища сам, тому воркер кладе в контейнер `apps/agent/payload/AGENTS.md`: де він (спільний контейнер, своя тека й гілка `agent/<id>`), що переживає сон, як працювати з git і GitHub (пуш лише у свою гілку, PR через `gh` або REST API), команди чату (`/stop`, `/delete`, `/update`) і що вони роблять з роботою, чого не друкувати (секрети), як завершувати (короткий підсумок українською, бо він іде в Telegram), а також що уточнення він ставить інструментом `question` (форма з кнопками в чаті), а не звичайним текстом у відповіді. Файл лежить у `apps/agent/payload/AGENTS.md`, а воркер розкладає його в `~/.config/opencode/AGENTS.md` (читає OpenCode) і `~/.claude/CLAUDE.md` (читає `claude` за провайдером Claude Agent). Це глобальний рівень; `AGENTS.md` самого репозиторію агент читає додатково. Змінюєш файл: достатньо `wrangler deploy`, образ і сесії не чіпаються.

## Запобіжники агента

- **Секрети.** У контейнер передається лише `OPENCODE_PASSWORD`, `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `GITHUB_TOKEN`, `CLAUDE_CODE_OAUTH_TOKEN` змінні публікації сайтів (`R2_*`, `SITES_BASE_URL`, `PUBLIC_*`) і доступ до Sure (`SURE_MCP_TOKEN`, `SURE_ACCESS_CLIENT_*`; білий список `containerEnv`, є тест). Токени Todoist і бота нотаток живуть в іншому воркері й у воркері агента їх немає; секрети чату (`BOT_TOKEN`, `TG_WEBHOOK_SECRET`, `CHAT_ID`) і Access до контейнера не потрапляють.
- **Гілки.** У образі системний `core.hooksPath` вказує на теку, куди воркер кладе `pre-push` (з `payload/`), що відхиляє пуш у `main` і `master`; агент працює в `agent/<id>`. Це запобіжник від випадковості (`--no-verify` його обходить), справжній захист налаштовується в GitHub: для кожного репозиторію, яким користується агент, увімкни **rule/branch protection** на `main` (вимагати PR, заборонити прямі пуші й force-push), а токен `GITHUB_TOKEN` зроби fine-grained лише для потрібних репозиторіїв із правами Contents і Pull requests (read/write), без Workflows і Administration. Токен не вміє пушити в захищену гілку.
- **Сон.** Контейнер засинає через годину без запитів (`AGENT_INACTIVITY_MS`); `exec`, відкриті з'єднання й SSE продовжують його життя (див. `GET /api/computer`).
- **Ліміти.** Поки хтось працює, alarm кожні 15 с перевіряє всі активні сесії (і з чату, і з веб-інтерфейсу): вартість понад `AGENT_MAX_COST_USD` (за замовчуванням 5) чи токенів (вхід + вихід + reasoning, без кешу) понад `AGENT_MAX_TOKENS` (за замовчуванням 3 млн) перериває сесію, а для сесій із чату приходить `⛔ Сесію зупинено: …`. Перша перевірка сесії з веб-інтерфейсу може відбутись із затримкою до 5 хв (до першого alarm). За підписки Claude `cost` у OpenCode може бути нульовим чи умовним, тож надійніший ліміт за токенами; реальні значення подивись у `/status`.

## Спостереження за затримками

Усі рядки затримок містять слово `latency` (Workers Logs → пошук `latency`, чи `wrangler tail` у `apps/agent`) і мітки часу UTC. Тексту повідомлень там немає.

- `latency telegram <чат>/<повідомлення>: …`: шлях вебхука. Поля: `flow` (`new-session` / `follow-up` / `ask-repo`), `kind` (voice/text/image), `sent` (коли повідомлення відправлено в Telegram), `lag-s` (скільки секунд минуло до початку обробки: доставка вебхука й черга), етапи `react`, `link`, `transcribe` (Whisper), `route` (LLM-роутер), `topic`, `post` (пост «⏳ Запускаю»), `begin` (передача в Durable Object), `start`/`end`/`total`.
- `latency job <id>: queued=…`: скільки завдання чекало на alarm у Durable Object від прийняття (`accepted`) до виконання; `cold=true`, якщо контейнер спав.
- `latency container: …`: лише холодний старт контейнера: `source` (snapshot/image), етапи `launch`, `ready` (OpenCode відповідає, модель доступна), `payload`.
- `latency session <id> start: …`: `container` (очікування контейнера), `queue` (черга серійних завдань), `prepare` (тека й клон), `create` (сесія OpenCode), `prompt` (відправка промпта).
- `latency session <id> first-busy=…`: від початку стеження (промпт відправлено) до першої ознаки, що модель працює.

Повна хронологія запиту: `sent` → `start` (lag) → `begin` → `accepted` → `queued` → `session … start` → `first-busy`.

Трейси Cloudflare (`[observability.traces]` у `wrangler.toml`) показують waterfall викликів воркера, Durable Object, R2 і `fetch`. Семплінг 0.2, бо інтерфейс OpenCode пінгує щосекунди; для розслідування конкретного запиту тимчасово постав 1.

## SSH у контейнер

`npm run ssh -w apps/agent` (сам знаходить інстанс `main`; зі своєю командою: `npm run ssh -w apps/agent -- ls /workspace`) або вручну `npx wrangler containers ssh <INSTANCE_ID>` (id: `npx wrangler containers instances`). Якщо ключ має пароль, додай його в агент: `ssh-add --apple-use-keychain ~/.ssh/id_ed25519` (інакше wrangler відповідає `Permission denied (publickey)`). Публічний ed25519-ключ лежить у `wrangler.toml` (`[[containers.authorized_keys]]`), порту назовні немає, вхід лише через твій акаунт Cloudflare. Контейнер має вже працювати: SSH його не будить і **не утримує від сну**. Зміни, зроблені через SSH, воркер не бачить, тож після роботи виконай `POST /api/computer/snapshot` (за Access), інакше вони зникнуть разом із диском при сні. Агент не має доступу до `wrangler` і акаунта Cloudflare.

Захист у два шари: Cloudflare Access перед воркером і перевірка його JWT (`Cf-Access-Jwt-Assertion`: підпис RS256 за ключами команди, `aud`, `iss`, `exp`) у самому воркері; без `ACCESS_TEAM_DOMAIN`/`ACCESS_AUD` воркер відповідає 503. Пароль OpenCode (basic auth) підставляє воркер, у браузері його вводити не треба.

## Налаштування (потрібні ваші дії)

```sh
# 1. Docker (Docker Desktop або Colima) має працювати: wrangler збирає образ із apps/agent/container/Dockerfile
cd apps/agent

# 2. Секрети
npx wrangler secret put OPENCODE_PASSWORD          # довгий випадковий рядок (пароль OpenCode V2, користувач завжди `opencode`)
npx wrangler secret put ANTHROPIC_API_KEY          # або OPENAI_API_KEY: ключ моделі для OpenCode; той самий OPENAI_API_KEY вмикає gpt-6-luna для маршрутизації задач і голосу в чаті (без нього Gemma 4)
npx wrangler secret put CLAUDE_CODE_OAUTH_TOKEN    # або замість ключа: токен підписки Claude (див. «Підписка Claude»)
npx wrangler secret put GITHUB_TOKEN               # необов'язково: для приватних репозиторіїв і пушу гілок

# 3. Деплой (перші хвилини після нього контейнери ще розгортаються)
npm run deploy
```

4. У Cloudflare Zero Trust створити застосунок Access (Self-hosted) для `agent.example.com` (або в налаштуваннях воркера увімкнути Cloudflare Access), політика: ваша пошта. З застосунку взяти **Application Audience (AUD) tag**, а team domain — `<team>.cloudflareaccess.com`.
5. `npx wrangler secret put ACCESS_AUD` і `npx wrangler secret put ACCESS_TEAM_DOMAIN`.
6. Перевірка (після входу через Access у браузері): `POST /api/sessions` з тілом `{"prompt":"…"}` (наприклад, з DevTools або `curl` із токеном Access Service Token) → відкрити `url` з відповіді з телефона.

Локально: `npm run dev -w apps/agent` (потрібен Docker; `LOCAL_DEV` вимикає перевірку Access).

## Відкриті питання прототипу

Перевірено на Cloudflare: кілька сесій в одному контейнері (worktree, порожня тека), прямі посилання `/s/<id>`, веб-термінал (WebSocket через проксі, потрібне прибирання `Origin`), SSH, ручний знімок, сон і відновлення зі знімком зі збереженням змін, зроблених через SSH. Не виміряно: ціна й холодний старт `standard-1`, час відновлення на великих репо. Відкрита вкладка, термінал чи SSH тримають контейнер від сну: стан дивись у `GET /api/computer`. Варіант без контейнера (OpenCode SDK у Durable Object) прибрано: без файлової системи, shell і git він не вміє клонувати репозиторії (є в історії git).

## Знімки диска (стан сесії між снами)

Контейнер засинає після години без запитів і втрачає диск (база OpenCode з історією, `/workspace`). Щоб сесія це пережила, `AgentSession` знімає диск знімками Cloudflare (`snapshotContainer`, політика `durable_object`):

- Після активності (`start`, `followUp`, зміни з веб-інтерфейсу) планується alarm через 5 хв. Якщо жоден агент не працює і з минулого знімка були зміни, диск знімається, а handle (`id`, образ, час) лягає в сховище Durable Object. Поки агент працює, alarm повторюється. Коли змін немає, alarm не перепланується (постійний alarm не давав би контейнеру заснути).
- Після сну `start`/`followUp`/веб-інтерфейс стартують контейнер зі знімка: ті самі сесії OpenCode з історією, клони й worktree, `entrypoint.sh` виконується знову (токен GitHub віддає credential helper з env (не `insteadOf`: той вшиває токен в URL, і `git remote -v` його друкує), на диск він не потрапляє, інтеграція `claude-agent` вже в базі й не підключається вдруге).
- Знімок відновлюється з образу, з якого створений (інший образ не підставляється), тож зміна Dockerfile сама сесій не скидає: новий образ застосовується командою `/update`. Якщо відновлення не вдалося (термін зберігання 30 днів від створення чи останнього відновлення), знімок видаляється й старт іде з образу.
- Знімок не містить пам'яті й процесів, секрети передаються `env` при кожному старті. Максимум 20 ГБ, диск `standard-1` — 8 ГБ.

Перевірено на Cloudflare: сесія з файлом пережила сон контейнера й відкрилась зі знімка з історією (тоді ще контейнер на сесію). Знімок порожнього клону (~21–23 МБ) створюється за 7–10 с. Час відновлення й вартість зберігання на великих репозиторіях не виміряні.

Підводні камені, на які натрапили:
- `monitor()` у `waitUntil` тримає Durable Object в пам'яті до 15 хв, і таймаут простою не стартує, тому ми його не викликаємо.
- Service worker OpenCode кешує оболонку застосунку й віддає її на `/s/<id>` (помилка «Unrecognised route»): запит не доходить до воркера. Воркер сам віддає нейтральний `/sw.js` без кешу.
- Для перевірки таймаути можна скоротити змінними `AGENT_INACTIVITY_MS` і `AGENT_SNAPSHOT_INTERVAL_MS` (`wrangler deploy --var …`).

## Підписка Claude замість API-ключа

З OpenCode 2.2.3 є провайдер **Claude Agent**: OpenCode запускає встановлений у контейнері незмінений `claude` (Claude Code) через Agent SDK і дає йому свої інструменти (файли, shell). Образ ставить `@anthropic-ai/claude-code` (`CLAUDE_CODE_VERSION` у Dockerfile).

1. На своєму комп'ютері: `claude setup-token` (вхід у браузері, токен видається приблизно на рік).
2. `npx wrangler secret put CLAUDE_CODE_OAUTH_TOKEN` (з теки `apps/agent`). Необов'язково `CLAUDE_MODEL` (`opus`, `sonnet`, `haiku`, `fable`; за замовчуванням `sonnet`).

Із токеном воркер передає його в контейнер, після старту підключає інтеграцію `claude-agent` (інтеграції завантажуються трохи пізніше за `/api/info`, тож підключення повторюється в циклі очікування) і створює сесії з моделлю `claude-agent/<модель>`. Без токена працюють ключі `ANTHROPIC_API_KEY`/`OPENAI_API_KEY`.

Ліміт контексту: воркер розкладає глобальний `~/.config/opencode/opencode.json` (`payload.ts`), де для моделей `claude-agent` (opus, sonnet, haiku, fable) вікно задано 272 000 токенів, а `compaction.auto` увімкнено: коли розмова наближається до ліміту, OpenCode сам стискає її (AutoCompact). Ліміт один на всі сесії; змінюється константою `CONTEXT_LIMIT`.

Перевірено на Cloudflare (workers.dev + Access): сесія створюється, веб-інтерфейс відкривається, агент на `claude-agent/sonnet` виконав задачу (створив файл і запустив `git`) через інструменти `write`/`shell`. Воркер після старту чекає, поки моделі провайдера з'являться (інакше `Model unavailable`).

Перевірено локально в Docker: сесія на `claude-agent/sonnet` відповідає, агент створює файли й запускає команди (інструменти `write`, `shell`).

**Ризик.** Anthropic забороняє пропускати чужі запити через підписку й пропонувати вхід через claude.ai іншим; вхід власника в незмінений Claude Code на власному хості її умови не забороняють, але публічно провайдер OpenCode вона не схвалювала, і умови можуть змінитись без попередження. Довгі автономні запуски можуть швидко вичерпати ліміти підписки. Токен дає доступ до підписки: зберігай лише в `.env` і `wrangler secret`.

## Версії OpenCode

Використовується лише **OpenCode V2**. Контейнер ставить `@opencode/cli` (версія зафіксована в Dockerfile, `OPENCODE_VERSION`), запускає `opencode serve --hostname 0.0.0.0 --port 4096` (веб-інтерфейс віддає сам сервер) і приймає basic auth з паролем `OPENCODE_PASSWORD`. Клієнт воркера працює з API V2: `GET /api/info` (готовність), `POST /api/session`, `POST /api/session/{id}/prompt`, `GET /api/session/active`, `POST /api/session/{id}/interrupt`; відповіді загорнуті в `{data}`. Варіант на SDK (`@opencode/sdk/workerd`) теж V2. V1 не підтримується.

Перевірено локально в Docker (образ `apps/agent/container`, `-e OPENCODE_PASSWORD=…`): `/api/info`, створення сесії з `location.directory`, `prompt`, `session/active`, `interrupt` і історія відповідають клієнту воркера; без пароля API дає 401; веб-інтерфейс (`/`, статика `/_assets/*`, SSE `/api/event`) працює з basic auth, тож `opencode pair` для проксі не потрібен. Не перевірено: WebSocket/SSE саме через `getTcpPort().fetch` у Cloudflare, холодний старт і ціна `standard-1`.
