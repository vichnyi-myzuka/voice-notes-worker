# Агент: чат у Telegram і GitHub

Керування агентом з Telegram і зв'язок GitHub → Telegram. Загальний опис агента — у [agent.md](agent.md).

## Чат з агентом у Telegram

Окремий бот (не бот нотаток) працює так само, як бот нотаток: канал `CHAT_ID` (бот адмін з правом видаляти повідомлення) і особистий чат із ботом від `TG_OWNER_ID`. Голосове чи аудіо розпізнає Whisper (Workers AI, українська), текст іде як є. Бот ставить ✍ і створює сесію (id `tg-<chat>-<message_id>`):

- **У каналі** оригінал замінюється постом: текст задачі (для голосового — репозиторій і гілка `agent/…` зверху, а `🗣` і розшифровка під ним у згорнутій цитаті) та посилання `https://agent.example.com/s/<id>`; оригінал видаляється. У канал дописують лише адміни, тож окремої перевірки відправника немає.
- **У приваті** бот відповідає посиланням (для голосового ще й показує, що розібрав), текстовий оригінал лишається, а голосове видаляється (розшифровка вже в пості).
- **Теми (threads) у приваті.** Якщо в чаті з ботом увімкнено режим тем, кожна нова сесія з головного чату отримує власну тему (`createForumTopic`, назва — коротка семантична назва задачі українською, яку дає той самий виклик моделі, що й назву гілки; без неї — початок тексту задачі): пост сесії, питання, підсумок і відповіді на команди йдуть у неї (`message_thread_id`), текст задачі стоїть у пості, а оригінал видаляється. Повідомлення в темі без reply — уточнення в сесію цієї теми (Durable Object шукає її за `chatId` + `threadId` у пості сесії, `byThread`), `/status`, `/stop`, `/model`, `/delete` теж працюють там без reply. Після кожного успішного ходу агента маленька модель (`container/title.ts`) бачить поточну назву, задачу, останнє уточнення й підсумок і лишає назву або оновлює її (`editForumTopic`), якщо напрям розмови змінився; назву пам'ятає пост сесії, теми, створені вручну, не перейменовуються, збій моделі чи Telegram назву не чіпає. Іконка теми показує стан сесії (`editForumTopic` з `icon_custom_emoji_id`, `setTopicIcon`): ⚡ працює, ❓ агент чекає відповіді, ✅ готово (чи зупинено), ❗ збій чи ліміт. Telegram дозволяє лише емодзі зі свого набору іконок тем (`getForumTopicIconStickers`), тому для кожного стану є запасний варіант, а якщо емодзі в наборі немає чи бракує прав, іконка лишається як була. Тема видаляється разом із сесією (`deleteForumTopic` у `remove`, тож це діє для `/delete`, кнопки, веб-інтерфейсу й мерджу PR). Якщо тем немає (режим вимкнено, `createForumTopic` не вдався), усе працює як раніше: пост у самому чаті. Повідомлення в темі, яка не належить жодній сесії (створена вручну), стартує сесію в цій темі без нової. Для каналу теми не використовуються.

**Кнопки під постом.** Пост сесії має inline-кнопки `⏹ Стоп` і `🗑 Видалити` (після завершення лишається `🗑 Видалити`): у каналі меню команд Telegram не підтримує, а кнопки працюють. Натискання приходить `callback_query` (вебхук має отримувати його в `allowed_updates`), кнопку приймаємо лише від власника (`TG_OWNER_ID`) у каналі `CHAT_ID` чи його приваті; результат показується спливаючою підказкою, у чат нічого не пишемо. Id сесії береться з посилання на неї, у `callback_data` лежить `stop:<id>`/`del:<id>`. **Питання агента.** Коли агент ставить питання (інструмент `question`, у V2 це форма, подія `form.created`), пост показує його одразу, без тротлінгу, з варіантами й підказкою відповісти на пост. Для простих питань (одне видиме поле: варіанти з одиночним вибором, так/ні або множинний вибір) під постом з'являються кнопки з варіантами. Множинний вибір: кнопки (`tog:<id>:<номер>`) перемикають варіанти (☑/☐ у підписі, поточний вибір у спливаючій підказці), `✅ Підтвердити` (`ok:<id>`) надсилає масив вибраних значень (вибір зберігає Durable Object, поки не підтверджено). Одиночний вибір: натискання (`ans:<id>:<номер>`) іде в `POST /api/session/<id>/form/<formID>/reply` (`answer`) і показується в пості (`⏳ Працює · відповідь: …`). Форма з кількома полями, де кожне має варіанти (чи так/ні), показується покроково: по одному питанню `(1/N)` з кнопками, а агентові всі відповіді йдуть разом після останнього. Форми з вільним текстом показуються текстом, відповідати на них треба відповіддю на пост. Якщо замість кнопки (чи на форму без кнопок) надійшла текстова відповідь, `followUp` спершу скасовує відкриту форму (`DELETE /api/session/<id>/form/<formID>?message=<текст>`), щоб агент не чекав на неї далі, а потім передає текст як звичайне уточнення. Питання, що лишилось без відповіді, втрачає актуальність із завершенням сесії.

Меню `/`-команд у приваті виставляється автоматично: перший вебхук кожного нового екземпляра воркера (тобто після деплою) викликає `setMyCommands` зі списку `COMMANDS` у `apps/agent/src/interface/telegram/handle.ts` (область `all_private_chats`; ідемпотентно, збій лише логується й повторюється з наступним вебхуком). Додаєш команду — додай її в `COMMANDS`, ручний виклик не потрібен. У каналі меню команд Telegram не підтримує.

**Холодний старт.** Запуск контейнера й клон репозиторію тривають хвилини, а `ctx.waitUntil` після відповіді вебхуку живе лише ~30 с (далі роботу мовчки обривають: лишалась реакція ✍ і нічого більше). Тому бот не чекає: розібравши завдання (Whisper, вибір репозиторію), він шле пост `⏳ Запускаю` і передає завдання Durable Object (`begin`; для уточнення `resume`). DO зберігає його як `job:<id>` і виконує в alarm (до 15 хв): пост стає `⏳ Запускаю контейнер`, потім `⏳ Працює`. Збій повторюється до 6 разів із паузою 15 с, після цього пост показує `⚠️ Не вдалося запустити агента`. `/delete` скасовує завдання, що ще не запустилось. Повторна доставка того самого повідомлення не створює другу сесію й другу відповідь (`begin` ідемпотентний; прийняте завдання `link` показує як `pending`). Чужі користувачі, інші канали й групи ігноруються мовчки; файл понад 20 МБ чи порожня транскрипція дають підказку без сесії. Telegram одразу отримує `200`, а Whisper і холодний старт контейнера йдуть у фоні (`waitUntil`).

- **Зображення.** Фото (стиснене чи надіслане «як файл» з `image/*`) йде агентові як вкладення, а не як опис: воркер завантажує його з Telegram (до 20 МБ) і передає в `POST /api/session/<id>/prompt` полем `files` (`data:`-посилання), тож модель бачить саме зображення. Підпис до фото — текст задачі чи уточнення (без підпису — типова фраза), Whisper не викликається. У завданні (`job:<id>`) лежать лише id файлів Telegram, самі файли завантажує Durable Object під час виконання (повтор безпечний). Повідомлення з фото, як і інші, видаляється після прийняття (і уточнення, і нова сесія): підпис до нього стоїть у пості сесії. У зворотний бік агент (за `payload/AGENTS.md`) пише в підсумку `![підпис](/шлях/до/файлу.png)` (чи https-адресу): воркер прибирає ці рядки з тексту поста, читає файл із контейнера (лише png/jpg/gif/webp із `/workspace` чи `/tmp`, до 10 МБ) і шле його в чат як фото (`sendPhoto`, у тему сесії; до 5 штук).

Керування сесією з чату:

- **Репозиторій.** Текст, що починається з `owner/name: задача`, відкриває сесію в worktree цього репозиторію (у пості з'являється `📦 owner/name`); без префікса задача йде в порожню теку. Для голосового префікс не розпізнається: репозиторій задавай текстом.
- **Уточнення.** Відповідь (голосом чи текстом) на пост бота з посиланням стає уточненням у ту саму сесію. Сесію бот знаходить за посиланням `/s/tg-…` у тексті поста, на який ти відповів (Telegram віддає його в `reply_to_message`), окремого сховища відповідностей немає. Відповідь на інше повідомлення — нова задача.
- **Модель.** Початок тексту `@opus задача` (чи `@провайдер/модель`, можна разом з репозиторієм: `@opus owner/name: задача`) запускає нову сесію на цій моделі (у пості `🤖 opus`); без префікса — `CLAUDE_MODEL` (за замовчуванням `sonnet`), а для задач із Sure чи Сільпо (явно чи за здогадом моделі) — `haiku`. Змінити модель наявної сесії можна командою **`/model opus`** відповіддю на її пост: діє з наступного ходу (поточний не переривається) і зберігається, тож нова сесія OpenCode після сну контейнера піде на ній. Недоступну модель бот відхиляє. Голосом «@» не продиктуєш, тож на початку розшифровки (і тексту) розпізнається й словесна форма: «модель опус, задача» (відомі назви: opus/опус, sonnet/сонет, haiku/хайку); невідома назва лишається в задачі. Змінити модель наявної сесії можна й через `/model`.
- **`/status`** (відповіддю на пост із сесією): ⏳ працює / 💤 чекає на відповідь / ✅ завершила / ❌ завершилась помилкою / ⏹ зупинена / 💤 контейнер спить, плюс вартість і токени. **`/stop`** перериває роботу; наступне уточнення продовжує її. **`/quota`** (без відповіді на пост) показує ліміти підписки Claude: для 5-годинного й тижневого вікон — смужка заповнення з 20 клітинок (`█████████████░░░░░░░`, 1 клітинка = 5%), точний відсоток використання і час до скидання. Окремого API немає, тож воркер робить найменший запит до `/v1/messages` (haiku, 1 токен) з `CLAUDE_CODE_OAUTH_TOKEN` і читає заголовки `anthropic-ratelimit-unified-*`; без токена підписки бот скаже, що ліміти недоступні.
- **Результат без запиту.** Після `start` і кожного уточнення Durable Object стежить за сесією. Він підписується на потік подій OpenCode (SSE `/api/event`), тож підсумок з'являється в пості одразу, щойно сесія завершилась (`session.execution.succeeded/failed/interrupted`), без очікування опитування. Потік відкритий лише поки є за чим стежити. Страховкою лишається alarm: поки сесія працює, він спрацьовує кожні 15 с (ліміти витрат, обрив потоку, подія до початку стеження), а коли робота закінчилась, у той самий чат іде підсумок: останнє повідомлення агента (до 3000 символів; там зазвичай посилання на PR) і посилання на сесію, або `❌ Помилка: …`. Якщо сесію зупинено вручну, повідомлення не приходить, а якщо контейнер зупинився посеред роботи, приходить попередження. Повідомлення, написане прямо у веб-інтерфейсі (`POST /api/session/<id>/prompt` через проксі) в сесію, що має пост у чаті, вмикає те саме стеження: пост показує стан, питання з кнопками й підсумок. Сесії без поста в чаті (створені через `/api/sessions`) не відстежуються. Саме повідомлення користувача в чат не дублюється.

Налаштування (один крок у Cloudflare, бо вебхук має йти повз Access):

1. У @BotFather створи **окремого** бота й візьми токен. Створи канал (приватний), додай бота адміном із правом публікувати й видаляти повідомлення, `CHAT_ID` каналу має вигляд `-100…`.
2. Секрети воркера: `cd apps/agent && npx wrangler secret put BOT_TOKEN`, так само `TG_WEBHOOK_SECRET` (довільний довгий випадковий рядок), `TG_OWNER_ID` (твій числовий id у Telegram) і `CHAT_ID`.
3. Cloudflare Zero Trust → Access → Applications → додай застосунок Self-hosted для `agent.example.com` зі шляхом `telegram` і політикою **Bypass** (Everyone). Без цього Access відповідає Telegram логіном, і вебхук не доходить. Решта хоста лишається за Access; `/telegram` захищає секретний заголовок `x-telegram-bot-api-secret-token`.
4. Вебхук: `source .env && curl "https://api.telegram.org/bot$AGENT_BOT_TOKEN/setWebhook" -d url=https://agent.example.com/telegram -d secret_token=$AGENT_TG_WEBHOOK_SECRET --data-urlencode 'allowed_updates=["message","channel_post","callback_query"]'` (`callback_query` потрібен для кнопок під постом; у `.env` значення агента під іншими іменами, ніж у бота нотаток).

## Автоматизація GitHub → Telegram

Вебхук GitHub `POST /github` (повз Access, як і `/telegram`; захист — підпис `X-Hub-Signature-256` за секретом `GITHUB_WEBHOOK_SECRET`) робить дві речі:

- **Прибирання після успішного деплою.** Коли workflow `deploy` на головній гілці завершився успішно, воркер знаходить за комітом PR (`GITHUB_TOKEN`), і для кожного PR з гілки `agent/<назва>` цього ж репозиторію (не форка) прибирає сесію так само, як `/delete`: сесія OpenCode, worktree, локальна гілка (за тих самих умов, що й у `CLEANUP`: робота не втрачена), оригінал у чаті, а також віддалена гілка в GitHub (уже видалену ігноруємо). Пост сесії згортається: скорочена шапка (завдання) і рядок `✅ Деплой успішний` з посиланням, підсумок агента прибирається; єдина кнопка `🗑 Видалити`. Невдалий деплой сесію лишає (можна дописати уточнення), а пост показує `❌ Деплой не вдався`. Якщо контейнер спить, прибирання чекає його запуску; `waitUntil` живе ~30 с, тож на холодному старті воно може не встигнути, тоді сесію видаль кнопкою `🗑`.
- **Схвалення деплою.** Коли job workflow чекає схвалення environment (`production-agent`; подія `workflow_job` зі статусом `waiting`), в особистий чат власника з ботом (`TG_OWNER_ID`; якщо його не задано, у `CHAT_ID`) приходить пост `🚀 Деплой чекає схвалення` з кнопками (а якщо деплой стосується PR сесії бота, то ці рядки й кнопки з'являються в пості самої сесії, окремого повідомлення немає) `✅ Схвалити` / `❌ Відхилити`. Натискання (лише від `TG_OWNER_ID`) викликає GitHub API `pending_deployments`, а пост показує результат; якщо GitHub відмовив, підказка містить причину (наприклад, `pending deployments 403`: токену бракує прав). Якщо environment уже схвалено на GitHub, кнопка скаже, що оброблено.
- **Результат деплою.** Коли workflow `deploy` на головній гілці завершився, в особистий чат власника (`TG_OWNER_ID`, інакше `CHAT_ID`) приходить `✅ Деплой успішний` / `❌ Деплой не вдався` / `⏹ Деплой скасовано` з посиланням на запуск і PR, що його запустив (шукається за комітом через `GITHUB_TOKEN`; якщо коміт пушили без PR, рядка PR немає). Пропущені запуски й інші workflow ігноруються. Під повідомленням є кнопка `🗑 Видалити` (лише від власника): прибирає його з чату. Якщо деплой стосується PR сесії бота, результат показується в пості сесії (див. вище), а якщо перед цим був окремий пост зі схваленням, результат дописується в нього, а не йде новим повідомленням.

- **Кнопка «🔀 Змерджити».** Коли агент успішно завершив роботу (`✅ Готово`) і в гілки сесії `agent/<назва>` є відкритий PR, під підсумком у пості сесії поруч із `🗑 Видалити` з'являється `🔀 Змерджити` (PR шукається через `GITHUB_TOKEN`; без токена, без PR чи при збої GitHub кнопки немає, а під підсумком з'являється рядок `ℹ️ Кнопку «Змерджити» не показано: <причина>`). Натискання (лише від власника) мерджить PR звичайним merge-комітом (`PUT /pulls/<N>/merge`), одразу (не чекаючи вебхука деплою) прибирає кнопку й дописує в пост рядок `🔀 PR #N змерджено, чекаємо на деплой` (його потім замінює статус деплою), а спливаюча підказка — `🔀 PR #N змерджено`; відмову GitHub (405/409) пояснює: воркер запитує PR і check-runs та збирає причини (конфлікти з основною гілкою, `CI не пройшов: <назви>`, `CI ще виконується`, чернетка, гілка відстає, правила гілки), показує їх спливаючою підказкою (до 200 символів) і повним списком окремим повідомленням у тому ж чаті (і гілці) (разом із текстом GitHub); кнопка лишається. Якщо причин не знайдено, підказка містить лише пояснення GitHub. Далі працює звичайний ланцюг: деплой, схвалення, прибирання сесії. Потрібні права `GITHUB_TOKEN`: Contents і Pull requests (Read and write).

Налаштування (кроки в GitHub і Cloudflare лише твої):

1. Секрети воркера агента: `npx wrangler secret put GITHUB_WEBHOOK_SECRET` (довільний довгий рядок) і `GITHUB_APPROVE_TOKEN` (fine-grained PAT на цей репозиторій: **Actions: Read and write**; належить тобі як рев'юверу environment; агент цього токена не бачить, у контейнер він не передається). Якщо в environment увімкнено «Prevent self-review», схвалити власний запуск не вийде.
2. GitHub → репозиторій → Settings → Webhooks → Add webhook: Payload URL `https://agent.example.com/github`, Content type `application/json`, Secret той самий, події: **Workflow jobs** і **Workflow runs** (Pull requests і Deployment reviews не потрібні).
3. Cloudflare Access: до політики Bypass для шляху `telegram` додай шлях `github`.
